# 导航系统配置方案：Profile 化安全与行为管理

## 0. 背景与目标 (Background & Objectives)

### 现状问题
当前系统的导航行为存在“编译期固定/代码内硬编码”的部分，存在以下局限：
- **扩展性差**：新增模式（例如更激进的穿越策略、不同的限速档位）需要修改代码、重新定义枚举并全链路重新编译。
- **配置分散**：行为参数散落在代码常量、YAML 参数和 Waypoint 属性中，难以统一管理。

### 目标
引入 **Profile（配置描述文件）** 概念，实现导航行为的**数据驱动**与**一体化配置**：
1.  **动态扩展**：通过 YAML 定义新的 Profile 即可新增模式，无需修改代码。
2.  **全栈聚合**：一个 Profile 完整描述 **安全策略 + Costmap 行为 + Controller 参数 + MCU 指令**。
3.  **高可用性**：支持 `fallback_profile` 机制，在超时或异常时自动降级到安全模式。

## 1. 总体架构 (Architecture Overview)

1.  **接口层升级**：将对外契约从 `uint8 mode` 升级为 `string profile`。
2.  **中心化管理**：`rc26_nav_mode_manager` 升级为 **Profile 解释器与执行器**：
    -   **加载**：解析 YAML 配置，构建 Profile 库。
    -   **执行**：响应 `SetNavMode(profile)` 请求，原子化执行配置应用（Layer 开关、清图、参数覆盖、MCU 指令下发）。
    -   **监控**：运行 Watchdog，负责超时熔断与自动回退。
3.  **业务层适配**：`rc26_decision` (Waypoint Navigator) 通过指定 `nav_profile` 驱动底层行为，不再硬编码逻辑。

## 2. 详细需求 (Requirements)

### 2.1 接口定义 (Interface Layer)
1.  **数据类型**：系统接口 SHALL 使用 `string profile` 作为模式标识（Profile 名称）。
2.  **服务增强**：`SetNavMode` 服务 SHALL 支持：
    -   `profile` (string): 目标配置名。
    -   `timeout` (float32): 临时覆盖 watchdog 超时（秒）；`<=0` 表示使用 Profile 默认值。
    -   `reason` (string): 切换上下文说明。
3.  **状态反馈**：`NavSafetyState` 消息 SHALL 包含：
    -   `current_profile` (string): 当前生效配置。
    -   `reason` (string): 触发原因（包括自动回退的原因）。
    -   `stop_required` (bool): 指示上层是否应立即停机。
    -   `timed_out` (bool): 指示是否处于超时回退状态。

#### 2.1.1 升级说明 (Migration Notes)
该变更为 **BREAKING CHANGE**：`rc26_interfaces` 中 `SetNavMode/NavSafetyState`（或等效消息）字段类型变化会要求所有依赖节点同步升级并重新编译。

### 2.2 Profile 配置规范 (Configuration Specification)
系统 SHALL 支持通过 YAML 定义 Profile 集合 (`profiles.<name>.*`)。每个 Profile 包含以下域：

#### 2.2.1 核心属性
-   `fallback_profile` (string): **必需**。发生异常（超时、执行失败）时的回退目标。
-   `watchdog` (object):
    -   `timeout_sec` (double): 最大保持时间。0 表示无限。
    -   `stop_required_on_timeout` (bool): 超时后是否请求停机。

#### 2.2.2 行为控制域
Profile 需统一配置以下子系统行为：
1.  **Precheck (前置校验)**:
    -   `require_stopped`: 是否要求切模前底盘停稳。
2.  **Costmap (地图行为)**:
    -   `drop_layer_enabled`: 是否启用 `drop_layer`（等价于 costmap 参数 `drop_layer.enabled`）。
    -   `clear_costmap`: 是否清除代价地图（建议明确是 local/global/both；当前实现以 local 为主）。
    -   `wait_rebuild`: 是否等待地图重建（需配合超时机制；当前可用“障碍话题时间戳更新”作为粗略确认）。
3.  **Controller (控制器参数)**:
    -   覆盖 Nav2 Controller Server 的参数（如 `xy_goal_tolerance`, `max_vel_x`）。
    -   **恢复机制**：切换 Profile 时，系统 MUST 能够应用新参数；切出时 SHOULD 恢复默认或应用新 Profile 的参数。
4.  **速度链路**：
    -   系统速度控制 MUST 仅通过 Nav2 输出 `/cmd_vel`，再由串口发送器下发 `POSE_TARGET(0x22)` 完成闭环；Profile 不直接下发任何“速度/模式”到 MCU。

#### 2.2.3 串口单一所有权 (Single Ownership)
系统 MUST 保证串口发送链路的 **单一所有权**：速度下发仅由 `/cmd_vel -> POSE_TARGET(0x22)` 这一路径完成，避免出现多路下行指令导致的冲突。

### 2.3 执行逻辑 (Execution Logic)

#### 2.3.1 切换序列 (Switching Sequence)
收到 `SetNavMode(profile=X)` 请求时，执行器 SHALL 按以下**原子序列**操作：
1.  **Validate**: 校验 Profile X 存在。
2.  **Precheck**: 检查前置条件（如停稳）。若不满足则拒绝。
3.  **Costmap Actions**: 执行 Drop Layer、Clear Costmap。
4.  **Parameter Apply**: 同步调用 Controller 参数设置服务。
5.  **State Update**: 更新内部状态为 X，重置 Watchdog。
6.  **Publish**: 发布新的 `NavSafetyState`。

*注：若序列中任一步骤失败，系统 MUST 保持原状态或回退到安全基线，并返回错误。*

#### 2.3.2 自动回退 (Auto-Fallback)
当 `watchdog` 超时或关键状态异常时：
1.  系统自动加载 `fallback_profile`。
2.  发布状态 `timed_out=true`, `reason="watchdog_timeout"`.
3.  若配置了 `stop_required_on_timeout`，上层决策模块应立即中断导航。

### 2.4 与 Waypoint 的集成
1.  **配置规范**：Waypoint YAML SHALL 使用 `nav_profile` 字段驱动底层 Profile 切换。
2.  **参数优先级**：
    -   Waypoint 现有 `tolerance` 字段（`xy`, `yaw`）在运行时动态映射到 Controller 参数。
    -   **冲突解决**：若 Profile 中也配置了 Controller 参数（如 tolerance），系统需明确优先级。
    -   *建议策略*：`nav_profile` 定义**基线参数**，Waypoint 的 `tolerance` 视为**单点覆盖 (Override)**，在 Profile 应用之后生效。

### 2.5 速度链路约束（统一由 Controller 输出）
本方案 **取消**“业务侧直接计算速度并发布 `/cmd_vel`”的路径，统一由 Nav2 `controller_server`（控制器插件）生成速度。

1.  **唯一来源**：系统 MUST 保证 `/cmd_vel` 的发布者为 Nav2 控制器链路（`controller_server`），业务模块不得直接发布 `/cmd_vel`。
2.  **下发链路（导航模式）**：系统 MUST 将 `/cmd_vel` 作为 MCU 目标速度入口，由串口发送器（如 `PoseSender`）订阅并通过协议 `POSE_TARGET(0x22)` 下发 `(vx, vy, wz)`。
3.  **速度调控方式**：Profile/Waypoint 的“速度效果”SHALL 通过控制器参数实现（如 `FollowPath.v_linear_max` / `FollowPath.v_angular_max`、速度缩放策略等），而不是绕过控制器直接给速度。
4.  **冲突视为错误**：若系统存在除 Nav2 外的 `/cmd_vel` 发布者（例如遥控节点），应视为配置错误（可能导致速度打架），需要通过改名/改话题隔离，而不是引入 mux 仲裁。
5.  **遥控隔离**：仓库内遥控节点（`rc26_telecontrol`）SHOULD 默认发布到 `/cmd_vel_teleop`（而非 `/cmd_vel`），确保不影响导航链路；需要遥控时应使用独立的启动配置与话题接线。
6.  **遥控/调试模式接线**：若需要使用 `/cmd_vel_teleop` 驱动底盘，应停止 Nav2（避免产生 `/cmd_vel`），并将 `PoseSender` 的 `cmd_vel_topic` 参数指向 `cmd_vel_teleop`（即订阅 `/cmd_vel_teleop` 后下发到 MCU）。

## 3. YAML 配置示例 (Example Configuration)

### 3.1 导航模式管理器配置 (`nav_mode_manager`)
推荐使用**独立配置文件**加载 Profile，以支持复杂结构（如 List-of-Map）。

`ros_params.yaml`:
```yaml
nav_mode_manager:
  ros__parameters:
    profile_config_file: "/path/to/nav_profiles.yaml"
    controller_server_node: "controller_server"
    # 下面这些参数当前在 rc26_nav_mode_manager 已存在，可继续复用
    costmap_node_name: "local_costmap/local_costmap"
    odom_topic: "odom"
    obstacles_topic: "terrain_obstacles"
    default_timeout_sec: 5.0
    stop_linear_eps_mps: 0.05
    stop_angular_eps_rps: 0.05
    param_timeout_sec: 2.0
    clear_timeout_sec: 2.0
    rebuild_timeout_sec: 0.5
```

`nav_profiles.yaml` (Profile 定义):
```yaml
profiles:
  # === 安全模式 (默认回退) ===
  safe:
    fallback_profile: "safe"  # 自指，防止无限递归
    precheck:
      require_stopped: false
    costmap:
      drop_layer_enabled: true
      clear_costmap: false
    controller:
      apply: false            # 不覆盖参数，使用默认
    watchdog:
      timeout_sec: 0.0        # 无超时

  # === 楼梯穿越模式 V2 ===
  stairs_traverse_v2:
    fallback_profile: "safe"
    precheck:
      require_stopped: true
    costmap:
      drop_layer_enabled: false
      clear_costmap: true
      wait_rebuild: true
      rebuild_timeout_sec: 0.5
    controller:
      apply: true
      params:
        # 覆盖 Controller Server 参数
        general_goal_checker.xy_goal_tolerance: 0.10
        general_goal_checker.yaw_goal_tolerance: 0.15
        FollowPath.v_linear_max: 0.5
        FollowPath.v_angular_max: 0.8
    watchdog:
      timeout_sec: 8.0
      stop_required_on_timeout: true
```

### 3.2 Waypoint 配置 (`rc26_decision`)
```yaml
static_points:
  climb_start:
    x: 10.5
    y: 2.0
    theta: 1.57
    strategy_tag: "TAG_STAIRS"
    
    # 指定使用的 Profile
    nav_profile: "stairs_traverse_v2"
    
    # [可选] 单点覆盖 Profile 中的 tolerance
    # tolerance: {xy: 0.05, yaw: 0.1}
    
    # 导航超时（业务层逻辑），与 Profile 的 watchdog 独立
    timeout_sec: 15.0
```

## 4. 验收标准 (Acceptance Criteria)
1.  **配置热加载**：修改 YAML 并重启节点后，新 Profile 能够被识别并执行，无需编译代码。
2.  **完整性验证**：切换 Profile 能正确触发 Costmap 清除、Controller 参数变更。
3.  **回退可靠性**：人为制造超时或指令失败，系统能自动回退到 `fallback_profile` 并发布报警状态。
4.  **错误处理**：
    -   请求不存在的 Profile -> 拒绝并报错。
5.  **一致性**：`rc26_decision` 通过 Waypoint 的 `nav_profile` 驱动 `SetNavMode(profile)`，且状态话题能反映 `current_profile`。

## 5. 可行性分析与不足补充 (Feasibility & Gaps)

### 5.1 与现有实现对齐（已具备能力）
- `rc26_nav_mode_manager` 现已具备：停稳判定、`drop_layer.enabled` 动态开关、清 local costmap、重建确认、以及 `MF_TRAVERSE/MF_EXIT` 超时回退到 `MF_SAFE` 并发布 `stop_required/timed_out`（见 `src/rc26_nav_mode_manager`）。
- `rc26_decision` 的 `SmartWaypointNavigator` 现已具备：按 waypoint 的 `tolerance/speed_profile/payload` 覆盖 `controller_server` 参数并在结束阶段恢复默认。

结论：Profile 化在工程上可分阶段落地——先“把散落配置聚合到 YAML 并驱动既有行为”，再逐步演进对外接口与字段。

### 5.2 关键不足与补充建议
1.  **发布/部署约束**：接口升级将导致所有相关节点需要同步编译与部署；上线应采用“整包升级 + 联调验证”的方式，避免部分节点仍使用旧接口导致系统不可用。
2.  **Controller/Costmap 动态参数的可变性**：参数是否能在运行时修改，取决于目标节点是否声明参数、是否允许动态更新、以及参数回调是否拒绝。建议：
    -   为可覆盖参数建立 allowlist（或按前缀白名单），并在失败时明确策略（失败即拒绝切换/降级/继续但告警）。
    -   明确“恢复默认”的来源：读取当前默认并缓存（参考 `SmartWaypointNavigator` 的 defaults 读取方式）或由配置文件提供。
3.  **原子性与回滚边界**：切换序列涉及参数服务与清图等阻塞调用，严格意义无法跨节点完全原子。建议以 `nav_mode_manager` 内部状态机保证“状态更新在成功后发生”，并在失败时回滚关键动作（例如 drop_layer 恢复、watchdog 取消、保持旧 profile）。
4.  **Watchdog 与业务超时的协同**：当前系统同时存在：
    -   `nav_mode_manager` 的超时回退（安全层）
    -   Waypoint `timeout_sec`（业务层）
    
    建议明确优先级：任意一方触发都应中断导航，且最终应回到 `fallback_profile`/安全基线，避免“业务已退出但安全模式仍处于放开状态”。
5.  **串口指令扩展的落地边界**：现有协议 `rc26_serial/protocol.hpp` 已定义大量 `CommandID` 且多数需要 ACK。若未来引入 Profile 驱动的 `commands: [{name, params}]`，需补充：
    -   `name -> CommandID` 映射（allowlist）与 payload 编码规则
    -   序列执行策略（逐条等待 ACK/失败是否中断/是否重试）
    -   串口单一所有权（速度下发仍必须保持 `/cmd_vel -> POSE_TARGET(0x22)` 单一路径）
6.  **配置校验与安全**：建议为 `nav_profiles.yaml` 增加：
    -   版本号与必填项校验（如 `fallback_profile`、watchdog 字段）
    -   `fallback_profile` 递归/环检测（避免无限回退链）
    -   数值单位与范围校验（速度/超时/容差等）
    -   未知字段/未知指令的处理策略（加载时报错 vs 执行时报错）
7.  **`/cmd_vel` 唯一来源约束**：本方案要求 `/cmd_vel` 仅由 Nav2 控制器输出；已将仓库内遥控节点默认输出改为 `/cmd_vel_teleop` 以避免冲突，但系统集成阶段仍需检查是否存在其它 `/cmd_vel` 发布者（否则会导致 `PoseSender` 下发通道收到交织速度）。

### 5.3 建议落地路线（分阶段）
1.  **Phase A（接口与链路打通）**：升级 `SetNavMode(profile)` 与 `NavSafetyState(current_profile)`，实现 `nav_mode_manager` 的 profile 加载与切换执行；同步修改 `rc26_decision` 使用 `nav_profile` 并完成全链路联调。
2.  **Phase B（能力补齐）**：完善 controller 参数覆盖/回滚、MCU 指令 schema + 校验 + 执行策略、以及 `fallback_profile` 环检测与配置校验。
3.  **Phase C（体验提升）**：在稳定后再考虑热加载/诊断可视化/更细粒度 costmap 清图策略等增强能力。

## 附录：现有参数映射说明 (Context)
*本节说明当前代码中 Waypoint 参数如何映射到底层，供 Profile 集成参考。*

**Tolerance (容差)**
-   **定义**: Waypoint YAML 中的 `tolerance: {xy: ..., yaw: ...}`。
-   **行为**: `SmartWaypointNavigator` 在导航启动前，将其分别映射为 Controller 的 `general_goal_checker.xy_goal_tolerance` 和 `yaw_goal_tolerance`。
-   **集成建议**: Profile 提供的 controller params 是**基类**，Waypoint 提供的 tolerance 是**实例覆盖**。执行顺序应为：`Apply Profile Params` -> `Apply Waypoint Tolerance`。
