## 0. 一句话结论（按 P0/P1/P2 分层交付）

- **P0（赛前必须）**：修复 `kfs_block_fuser` 概率释放死锁、修复 `terrain_semantic` 的台阶 EMA 冻结、修复 bringup「Nav2 先动 / Keepout 后到」窗口，并补齐 MF 冷启动门控（禁区未就绪 → 必须停）。

## 1. 评分表条目 → 本方案闭环映射（100 分对齐）

为避免“只写方向、不闭环”，每个评分点都落到：**改什么（参数/代码/启动顺序）→ 怎么验证（指标/场景）**。

### 1.1 物理属性与传感器边界（30）

1) **EMA 跳变保护 vs 200mm 台阶（10）**：`terrain_semantic` 的 `jump_thresh_m` 与台阶高度冲突，需引入“台阶工况”门控与姿态/急停补偿（见 §3.1、§6.1）。  
2) **BFS 去噪 vs 稀疏边界（10）**：`min_obstacle_area_cells` 必须按工况/模式切换，MF 近场允许单格保留（见 §3.2、§6.2）。  
3) **近场盲区 + 强反光（5）**：对 0.1~1m 劣化区引入 Near-zone 自适应与异常点抑制（见 §3.3、§6.3）。  
4) **对角盲区兜底（5）**：禁止 MF 工况对角切角 + 角点守门（见 §3.4、§6.4）。

### 1.2 竞赛逻辑与空间几何（30）

5) **Keepout 膨胀与合法抓取兼容（10）**：Keepout 形状/裕量必须与方块几何、机器人接触几何一致，避免相邻空块不可达（见 §4.1、§6.5）。  
6) **KFS 概率释放死锁（10）**：`kfs_block_fuser` 现有“向 P=0.5 衰减 + free_thresh=0.35”在仓库代码中会导致**永不释放**（见 §4.2、§6.6）。  
7) **感知链路溯源与冷启动安全（5）**：明确 `merlin_map` 的生成/更新责任，禁区未闭环不得放行运动（见 §5.1、§5.2）。  
8) **赛场标定与队伍防错校验（5）**：`MfKfsState.team` 必须与 `mf_grid_layout` 镜像/版本强校验，标定异常直接进入安全停机/保守模式（见 §4.3、§6.7）。

### 1.3 混合系统架构与时序鲁棒（25）

9) **启动顺序控制（10）**：bringup 中 Keepout 链路需在 Nav2 前就绪，且决策侧必须做放行门控（见 §5.2）。  
10) **高速动态更新与总延迟（10）**：/mf_kfs_state 保底 5Hz + 端到端 SLA ≤300ms（见 §5.3、§6.8）。  
11) **跨系统 IPC 抖动防丢包（5）**：TerrainModeAdapter 参数下发要可重试/可确认，避免 80ms 静默超时（见 §5.4、§6.9）。

### 1.4 热边界与高负载（15）

12) **降频热负荷冗余（10）**：必须给出降频（latency 上移）下仍能维持 Keepout+跌落避障的轻量 fallback（见 §5.5、§6.10）。  
13) **延迟超限干预动作（5）**：`terrain_semantic` 超过 20ms 不得只打日志，必须触发限速/降载/停机（见 §5.6、§6.11）。

## 2. 系统闭环（必须被门控的三条链路）

### 2.1 KFS 禁区闭环（规则硬约束）

```text
Vision/ScanSurroundings → merlin_map(blackboard)
        ↓
decision_node 发布 /mf_kfs_state (rc26_interfaces/MfKfsState, 含 team)
        ↓
kfs_block_fuser 融合 → 发布 /kfs_filter_mask (OccupancyGrid, transient_local)
        ↓
nav2 KeepoutFilter 订阅 /costmap_filter_info + /kfs_filter_mask
        ↓
local/global costmap 生效 → planner/controller 输出运动
```

**硬约束 I-KFS-1（放行条件）**：在第一次允许任何导航目标/速度指令前，必须同时满足：
- `/costmap_filter_info` 已发布且 Nav2 KeepoutFilter 已接收；
- `/kfs_filter_mask` 已发布，且 **age ≤ 300ms**（P95 ≤ 200ms）；
- KFS 概率融合器不存在“永不释放”逻辑（见 §4.2）。

### 2.2 地形跌落/障碍闭环（运动安全约束）

```text
registered_scan → terrain_semantic → terrain_obstacles/terrain_drop → Nav2 costmap
```

**硬约束 I-TERR-1（台阶工况）**：200mm 台阶过渡不得触发长期冻结；冻结（若保留）必须有上限（≤300ms），并可被“台阶工况门控”解除。

### 2.3 模式/降级闭环（工程约束）

```text
nav_mode_manager(set_nav_mode) → 发布 nav_safety_state
        ↓
terrain_mode_adapter → set_parameters(terrain_semantic)
        ↓
速度/unknown_policy/去噪/阈值随 profile 切换
```

**硬约束 I-IPC-1**：跨系统抖动下，模式切换必须 **可重试+可回读校验**；失败必须触发 fallback profile（safe）或 stop_required。

## 3. 物理参数冲突修复（P0）

### 3.1 EMA 跳变保护：从“冻结台阶”改为“台阶工况可通过”

**现状（仓库实现）**：`src/rc26_terrain/src/terrain_semantic_node.cpp` 的 EMA 跳变保护为：
- 当 `|ground_z - ground_z_filtered| > jump_thresh_m(默认 0.15)` 时跳过 EMA 更新；  
在 200mm 台阶场景下会出现**持续跳过**（等价长期冻结）。

**P0 改造目标**：满足评分表“0.20m 台阶 + 急停俯仰误差 + IMU 漂移”的三要素，落地为三层门控：

1) **阈值上调（必要非充分）**  
`jump_thresh_m: 0.15 → 0.23`（建议先以参数落地，作为赛前最低修复）。

2) **台阶工况门控（速度/模式/稳定性）**  
新增/复用信号（任选其二即可闭环）：
- 来自 Nav profile：`stair_up/stair_down/mf_traverse` 视为台阶/高风险工况；
- 来自里程计速度：`v > v_stair_gate(建议 0.25m/s)` 视为跨越过程；
- 来自 base_ground 稳定标志（若接入）：急停/姿态不稳窗口单独处理。

门控行为：
- 台阶工况：**不冻结**，改为慢速 EMA（如 `alpha_slow=0.25`）加速收敛；
- 静止工况：仍允许冻结，但必须受“冻结最大持续时间”限制。

3) **姿态/急停补偿（对抗俯仰引入的伪跳变）**  
新增 pitch 补偿开关：对每个 cell 使用
\[
z_{corr}=z_{raw}-d_{horiz}\cdot \tan(pitch)
\]
其中 `d_horiz` 为 cell 到 base 的水平距离（由 cell index 可得）。急停导致的 pitch 瞬变将不再被误判为地形跳变。

> 交付形态：**参数表 + 小幅代码改造**（需要在 terrain_semantic 内部持久化 `last_pitch`/`last_speed` 并在 `estimateCellHeights()` 中使用）。

### 3.2 BFS 去噪：按 profile 切换，MF 工况允许单格保留

**现状**：`min_obstacle_area_cells=2`，BFS 使用 4 邻域清除小连通域，存在“真实台阶边缘单格投影被删”的风险。

**P0 配置策略（直接可由参数服务动态下发）**：

| Nav profile | 目标场景 | `min_obstacle_area_cells` | `obstacle_neighbor_mode` |
|---|---|---:|---|
| `mf_traverse` / `mf_approach` | 方块密集 + 近场稀疏 | **1** | `edge8`（同时缓解对角盲区） |
| `normal` | 开阔地/反光噪点更多 | 3 | `edge4` |
| `safe` | 降级保守 | 1 | `edge8` |

> 落地方式：扩展 `terrain_mode_adapter` 的 profile 映射，使其除 `unknown_policy/drop_forward_sector_deg` 外，同步下发 `min_obstacle_area_cells`、`obstacle_neighbor_mode`、`jump_thresh_m` 等关键参数（见 §5.4）。

### 3.3 近场盲区 + 强反光：Near-zone 自适应与异常点抑制

**问题边界**：Mid-360 在 0.1~1m 近场存在精度劣化；顶面高反光会导致离群点，进而污染地面/顶面分位数估计。

**P0 最小可交付（不引入新传感器）**：
- **Near-zone 自适应**：当 `d_horiz < 0.6m`（可从 cell index 推出）时，动态放宽：
  - `min_points_per_cell: 5 → 3`
  - `ground_quantile: 0.25 → 0.15`
  - `min_obstacle_area_cells: 强制=1`
- **上限保护**：为 `top_z` 引入与 `ground_z_filtered` 的最大差值上限（如 `max_block_height_m=0.70`），避免反光伪高点穿透。

**P1 增强（需要代码把点类型切到 PointXYZI）**：
- 加入 intensity 异常裁剪/降权（滑动窗口分位数阈值）。

### 3.4 对角/角点兜底：禁止切角 + 角点守门

**风险**：在 MF 区方块/台阶角点处，Nav2 的路径平滑/控制器可能出现“切角”，使机器人在几何上跨越对角高差或擦边进入禁区。

**P0 兜底策略（不依赖建模完美）**：
- **MF profile 下扩大 drop 观测扇区**：`drop_forward_sector_deg=360`（覆盖侧向/后向跌落风险）；
- **MF profile 下启用 conservative unknown**：`unknown_policy=conservative`，unknown 输出到 `drop`（与跌落层一致）；
- **MF profile 下 obstacle 使用 edge8**：对角高差不再被 4 邻域遗漏。

**P1 守门（推荐）**：
- 在决策侧对 MF 点位生成加入“禁止对角连线”的约束：相邻格移动仅允许走中心-中心的轴向路径（并在点位层面增加中继点，避免 planner 直连切角）。

## 4. 竞赛几何约束修复（P0）

### 4.1 Keepout 形状/裕量：从“固定圆膨胀”改为“方块几何 + 可达性校验”

**现状风险**：
- `kfs_block_fuser` 默认 `inflate_radius_m=0.60` 且掩码分辨率 `map_resolution=0.05`（与 costmap 0.1 不一致），易造成“相邻空块不可达/规划死锁”和不必要的 IPC 负担。

**P0 方案（推荐）**：
1) **分辨率对齐**：`map_resolution: 0.05 → 0.10`（与 `nav2_params.yaml` 的 local/global costmap resolution 对齐）。  
2) **从圆形改为方块几何**：Keepout 应覆盖“方块顶面投影”，而不是圆形半径近似；引入：
   - `block_half_size_m = 0.60`（赛场几何常量）
   - `keepout_margin_m = 0.02~0.05`（由标定误差预算决定）
   Keepout 区域 = 方块外接正方形（或轴对齐矩形）+ margin。
3) **可达性校验**：对“紧邻 KFS 的空块侧向抓取站位”做离线检查（见 §6.5），确保 Nav2 有解且不贴边违规。

> 注：若短期无法改形状，最低要求是：减小无依据的“额外膨胀裕量”，并把可达性作为硬验收。

### 4.2 概率释放死锁：修复 `kfs_block_fuser` 的“永不释放”逻辑

**仓库现状（必须正视）**：  
`src/rc26_kfs_keepout/src/kfs_block_fuser.cpp` 的逻辑为：
- 先验 `P=0.5`；仅存在 hit（`lo += lo_hit`）；  
- `decayTimer()` 把 log-odds **衰减回 P=0.5**；  
- 但 `free_thresh=0.35 (<0.5)`，因此 **永远不可能衰减到释放阈值** → blocked 一旦成立就“永久禁区”。

**P0 修复（两条路，至少选一条落地）**：

方案 A（推荐，结构性正确）：
- 将衰减目标从 `P=0.5` 改为 `P=0.0`（或 `P=0.05`），确保在无新证据时能穿越 `free_thresh`；
- 增加 `ttl_sec`：任意 grid 若 `last_hit_age > ttl_sec` 强制释放（防止通信中断造成永久禁区）。

方案 B（参数级快速止血，赛前可用）：
- 保持向 `P=0.5` 衰减，但把 `free_thresh` 调到 **略高于 0.5**（如 0.55），形成可回落滞回带：`block_thresh(0.70)` / `free_thresh(0.55)`；
- 同时引入 `ttl_sec` 作为最后兜底。

**拾取强制释放（强烈建议）**：
- 当 `GrabKFS` 成功且确认来自某 `grid_id` 时，向 keepout 融合器发送“强制释放该格”的事件（topic/service 均可），将释放时延压到 200~500ms 量级，避免幽灵禁区阻塞后续路径。

### 4.3 标定与队伍镜像强校验：把“防错”变成硬约束

**必须解决的现实问题**：
- `mf_grid_layout.yaml` 目前是占位坐标，文件格式合法就会启用 keepout；一旦未标定即上场，禁区会系统性错位。
- `MfKfsState.team` 已存在但未被 keepout 侧使用，镜像赛场换边容易误配。

**P0 交付要求**：
1) `mf_grid_layout.yaml` 增加元信息并校验：`team/layout_version/validated`（或等价字段）。  
2) `kfs_block_fuser` 启动时执行几何自检：  
   - 相邻格中心距是否接近 1.2m（容差如 ±0.05m）；  
   - 未通过则 `keepout_enabled=false` 并发布 ERROR diagnostics；  
3) keepout 侧强校验 `msg.team` 与 layout team：不一致则进入 stop_required 或至少切 safe profile（赛前必须明确规则）。

## 5. 混合系统时序与鲁棒性（P0/P1/P2）

### 5.1 感知链路溯源：`merlin_map` 的责任边界（必须写清）

在仓库实现中：
- `merlin_map` 是 `rc26_decision` 黑板对象（见 `src/rc26_decision/src/mf/mf_area.cpp` 的 `MerlinMapManager`）；  
- 当前 `ScanSurroundingsAction` 仅初始化高度矩阵，**扫描/视觉更新 KFS 状态仍是 TODO**；  
因此若不补齐，`decision_node` 的 `/mf_kfs_state` 可能长期为空，Keepout 形同虚设。

**P0 要求**：明确并实现至少一种来源，使 `merlin_map->setKFS(grid_id, type)` 能在 MF 冷启动阶段被填充：
- 方案 1：补完 `ScanSurroundingsAction`，驱动 `rc26_vision::VisionInferenceManager`（merlin_model）对 12 格做一次扫描并落盘到 `merlin_map`；  
- 方案 2：新增独立“MF KFS 感知节点”发布网格级结果，决策侧订阅后更新 `merlin_map`。

### 5.2 启动门控：实现“先禁区、后运动”（必须消灭窗口）

**仓库现状**：`bringup.launch.py` 当前顺序为 `nav2_launch` 在 `kfs_block_fuser` / `costmap_filter_info_server` 之前启动，存在「导航已激活但禁区未到位」窗口。

**P0 改造**（两层同时做，避免单点失败）：

1) **Bringup 顺序调整（推荐）**  
将以下组件移动到 `nav2_launch` 之前启动并确保可用：
- `map_server_node` + `costmap_filter_info_server`（由 lifecycle manager 托管）  
- `kfs_block_fuser_node`  
- `nav_mode_manager_node`（用于统一发布 stop_required/safe）  

2) **决策侧放行门控（必须有）**  
在 MF 相关导航动作前增加 `INIT_WAIT` 条件：
- 已收到 `/costmap_filter_info`  
- 已收到 `/kfs_filter_mask` 且新鲜度满足阈值（age < 300ms）  
未满足：保持 `set_nav_mode safe` + 不发 Nav2 goal；超时进入“保守扫描/原地等待/虚拟围栏”策略。

### 5.3 动态更新：把 2Hz 采样窗口压到 5Hz（端到端 ≤300ms）

**P1 建议**：
- `decision_node` 的 KFS 定时发布：500ms → **200ms（5Hz）**；QoS 深度改为 1~3（最新优先），并保留“状态变化立即发布”。  
- Keepout SLA 指标（见 §6.8）纳入赛前压测：从 KFS 状态变化到 costmap 生效 P95 ≤ 300ms。

### 5.4 IPC 抖动：TerrainModeAdapter 参数下发要可重试/可确认

**仓库现状**：`terrain_mode_adapter` 使用 `future.wait_for(80ms)`，超时直接返回，属于“静默失败风险”。

**P0/P1 修正策略**：
- `wait_for_service`: 100ms → 120ms（并允许重试）；  
- `set_parameters`：单次 120ms，失败重试 2 次（间隔 30ms）；  
- 成功后 `get_parameters` 回读校验（50ms）；  
- 若最终失败：发布 WARN/ERROR 诊断，并触发 `set_nav_mode safe`（或设置 stop_required）。

同时把 profile 映射扩展为（至少）：
- `unknown_policy`
- `drop_forward_sector_deg`
- `min_obstacle_area_cells`
- `obstacle_neighbor_mode`
- `jump_thresh_m`

### 5.5 热降频下的轻量 fallback（必须能跑完 4 分钟）

**目标**：当 `terrain_semantic` P95 从 15ms 上移到 30~40ms 时，系统不能仅报警；必须自动进入“轻量但保安全”的配置。

**P2 轻量 fallback（建议做成 profile 或状态机动作）**：
- terrain_semantic：
  - `voxel_leaf_size_m: 0.05 → 0.08~0.10`
  - `perception_radius_m: 3.2 → 2.5`
  - `min_points_per_cell: 5 → 3`
  - `unknown_policy: conservative`（宁可停/绕，不可盲冲）
- Nav2 local_costmap：
  - `update_frequency: 20Hz → 15Hz`
  - `obstacle_max_range: 4.0 → 2.5`
  - `raytrace_max_range: 5.0 → 3.0`
- 决策/模式：
  - 强制 `set_nav_mode safe`（限速），必要时 stop_required。

### 5.6 延迟超限干预动作：把 `latency_error_ms=20` 变成硬触发

**仓库现状**：`terrain_semantic` 仅在 diagnostics 中标记 “处理延迟超限”，没有动作闭环。

**P2 要求**：当满足任一条件时触发动作（优先级从高到低）：
- `terrain_latency_ms > 20ms` 持续 N 帧（建议 N=3）  
- `age_mask_ms > 600ms` 或连续 deadline miss  
- CPU 降频进入阈值（如 prime < 2.0GHz）并伴随 latency 上移  

动作集合（至少落地一条）：
- 自动切 `safe` profile（限速）；
- 进入 Degraded-L2：stop_required + 等待链路恢复；
- terrain_semantic 启用 `fail_safe_strategy=virtual_fence`（仅在确实无法保证安全时）。
