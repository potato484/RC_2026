## 改进项清单

### P0 — 赛前必完成

#### I1. 绑架检测加速（kidnap detection）

**问题**: 当前 5 帧触发 + 0.5 阈值，确认绑架偏慢且可能导致“带病更新 map→odom”。
**根因**: 阈值为通用场景设计，竞赛绑架来源唯一（规则重试区），误触发风险极低。

**关键事实（用于校正预期）**：
- `rc26_localization` 的局部配准默认为 **2Hz（500ms 一次）**，确认延迟近似：`T_confirm ≈ kidnap_threshold_count / 2Hz`。
- 绑架检测使用的量是局部 small_gicp 的 **normalized_error（平均每内点误差，单位 m）**，不是 ICP fitness。

**改动** (`src/rc26_bringup/config/localization.yaml`):

```yaml
# 当前值 → 建议值
kidnap_threshold_count:   5 → 3      # 连续 3 次局部配准高误差触发（2Hz 下约 1.5s）
kidnap_fitness_threshold: 0.5 → 0.3  # 更严格阈值，提升灵敏度（需结合 bag 回放再定）
num_yaw_hypotheses:       4 → 8      # 45° 间隔搜索，覆盖不确定朝向
```

**必须补齐的工程细节：质量门控（防止“边坏边写”）**  
仅降低阈值会让触发更快，但误差升高期间若仍持续更新 `map→odom`，会造成 TF 跳变、规划/控制抖动。建议在 `rc26_localization` 增加“冻结更新”门控：

伪代码逻辑：
```text
performRegistration():
  result = align()
  normalized_error = result.error / max(1, result.num_inliers)

  if (normalized_error > freeze_update_err) or (result.num_inliers < min_inliers):
      hold(map_to_odom)                 # 不更新 result_t_ / previous_result_t_
      high_err_count++
  else:
      accept(map_to_odom = result.T)    # 正常更新
      high_err_count = 0

  if high_err_count >= kidnap_threshold_count:
      trigger_global_relocalization()
```

参数建议（需要新增到 `localization.yaml` 并在代码中读取）：
- `freeze_update_err`: `0.25 ~ 0.35`（按场地数据调整）
- `min_inliers`: `200 ~ 500`（按降采样后点数调整）
- `registration_timeout_sec`: 建议 `10.0 → 2.0 ~ 4.0`（让“持续未收敛”更快进入重定位）

#### I2. 重试区先验初值注入

**问题**: 当前全局重定位在全图搜索（ISS+FPFH+SAC-IA+NDT+ICP），耗时 1–3s。
**方案**: 将规则固定的重试区坐标作为初始候选，跳过全局检索，直接进入精化。

两阶段流程：
```
绑架检测触发
    │
    ├─ 先验快速通道：写入重试区固定坐标（2–4 个朝向候选）
    │       ↓ NDT + ICP 精化（~0.3s）
    │
    └─ 降级全局通道：ISS+FPFH+SAC-IA+NDT+ICP（当快速通道 fitness > 阈值时触发）
```

**所需信息**: 建图阶段标定重试区中心点的 map 坐标（x, y）及入场朝向（yaw）。

**落地路径（优先推荐）**：复用现有 `initialpose` 接口  
`rc26_localization` 已订阅 `initialpose`（RViz 默认发布 `/initialpose`），收到后会直接重置 `map→odom`，可做到“无需等待绑架检测”。

建议在“重试启动/裁判搬移复位”流程中由上层节点发布重试区先验位姿（带少量 yaw 候选），并以配准质量门控确认生效。

发布策略（建议 2–8 个 yaw 候选，谁先通过门槛谁生效）：
```text
on_retry_start():
  yaw_candidates = [yaw0, yaw0+90°, yaw0+180°, ...]   # 由规则/放置习惯决定
  for yaw in yaw_candidates:
    publish(initialpose(map, x_retry, y_retry, yaw))
    sleep(0.2~0.3s)
    if normalized_error < good_th:
        break
```

若必须在 `performGlobalRelocalization()` 内做“先验快速通道”，建议两阶段：
```text
fast_channel():
  candidates = [(x_retry, y_retry, yaw_k)]  # 2~8个
  for c in candidates:
    T0 = SE3(c)
    T1 = NDT(source, map, init=T0)          # 可选
    T2, score = ICP(source, map, init=T1)
    keep best(T2, score)
  if best_score < fast_accept_th:
    set map->odom = best_T; return SUCCESS
  else:
    return FAIL
```

建议新增配置（便于复现、便于换场地）：
```yaml
retry_zone:
  enable: true
  pose_xy: [x_retry, y_retry]         # 建图后测得
  yaw_candidates_deg: [0, 90, 180]    # 方向已知可缩到 1~2 个
  good_th: 0.25                       # normalized_error 门槛（需离线验证）
  fast_accept_th: 0.15                # ICP score 门槛（需离线验证）
```

#### I3. 对抗区亚克力幽灵点过滤

**问题**: 10mm 亚克力护栏产生透射幽灵点，污染 BZ 区配准，与算法选择无关（LIO 通用问题）。

**三层过滤策略**（按实现难度递增）:

| 层 | 方法 | 实现位置 | 优先级 |
|----|------|---------|--------|
| **L1** | 空间 ROI 剔除：对已知护栏坐标后方 ±0.3m 区域内的点直接丢弃 | localization.cpp 点云回调 | P0 |
| **L2** | 强度统计过滤：离线统计 MID-360 对亚克力回波的 intensity 分布，设过滤区间 | preprocess/点云预处理 | P0 |
| **L3** | 时序一致性过滤：对短时出现又消失的点（帧间存在时间 < N 帧）降权 | localization.cpp | P1 |

> **注意**: L2 需要真实点云数据离线拟合，不能使用拍脑袋阈值。收集方法：在 BZ 区对护栏做静态扫描，导出 intensity 字段分布。

**必须补齐的工程细节：字段链路与实现位置选择**  
当前 `rc26_localization` 将输入点云转换为 `pcl::PointXYZ`，会丢失 `intensity` 字段；因此：
- 若要做 **L2 强度过滤**，优先放在 Point-LIO preprocess（点型天然带 intensity）。
- 若要在后端做 L1/L3，优先在 `PointCloud2` 层用迭代器保留字段，或把后端点型改为 `PointXYZI`。

**L1：ROI（map 坐标）过滤建议写成“可配置盒体”**  
用若干个 AABB 盒体近似“护栏后方幽灵点区”，实现简单、可复现：
```yaml
acrylic_filter:
  enable: true
  roi_boxes_map:
    - {min: [x1, y1, z1], max: [x2, y2, z2]}
    - {min: [x3, y3, z3], max: [x4, y4, z4]}
```

ROI 过滤伪代码（注意：需要用当前 `map→odom` 把点投到 map）：
```text
for p_odom in cloud:
  p_map = T_map_odom * p_odom
  if in_any_box(p_map, roi_boxes_map):
      drop
  else:
      keep
```

**L2：强度阈值如何“用数据拟合”（最小闭环）**  
离线采样后至少产出两条曲线：`I_acrylic` 与 `I_normal` 的直方图/分位数，然后给过滤规则：
```text
if in_acrylic_roi and intensity in [I_low, I_high]:
    drop
```
建议先用分位数设初值：`I_low = P5(I_acrylic)`，`I_high = P95(I_acrylic)`，再在 bag 回放中调到“定位误差最小/跳变最少”。

**L3：时序一致性（不依赖强度）**  
用体素栅格维护“出现帧数”，只保留持续存在的点（幽灵点/动态遮挡往往寿命短）：
```text
voxel_id = floor(p_map / voxel_size)
voxel_age[voxel_id] = min(voxel_age+1, age_cap)

keep point iff voxel_age[voxel_id] >= N
```
推荐：`voxel_size = 0.15~0.25m`，`N = 3~5`（结合点云频率/局部配准频率再调）。

### P1 — 赛前推荐完成

#### I4. Point-LIO 点云最大距离限制

**问题**: MID-360 测距 40m，场地仅 12m×12m，远距离点引入噪声与对手机器人干扰。

**重要说明（避免无效改参）**：
- Point-LIO 预处理的距离门限来自 `Preprocess::det_range`（默认 1000），且该值目前 **未通过 YAML 暴露**。
- 因此方案里写的 `preprocess.max_range` 需要先实现参数读取，否则改 YAML 不生效。

**推荐改动 A（最优，改 Point-LIO 后生效）**：新增 `preprocess.det_range` 参数  
目标：让距离过滤在最前端发生，降低后续所有链路的噪声与 CPU。

建议配置（实现后写入 `src/point_lio/config/mid360.yaml`）：
```yaml
preprocess:
  blind: 0.5       # 最小距离（已有）
  det_range: 9.0   # 最大距离（建议 8~10m 试扫）
```

**备选改动 B（无需动 Point-LIO）**：在 `rc26_odom_interface` 做距离过滤  
在转发 `/cloud_registered → /registered_scan` 时丢弃远点（缺点：不会降低 Point-LIO 自身负担，但能减少后端匹配噪声）。

距离过滤伪代码：
```text
for p in cloud:
  r2 = x*x + y*y + z*z
  if r2 < blind^2 or r2 > det_range^2: drop
  else: keep
```

#### I5. 分区匹配权重策略

**背景**: 三区定位难度与点云质量差异显著。

| 区域 | 点云质量 | 建议策略 |
|------|---------|---------|
| MF (梅林) | 优（12 个方块强几何特征） | 正常权重，建图时保证台阶边缘密度 |
| MC (武馆) | 差（平坦，少特征） | 依赖后端先验 + 高 num_yaw_hypotheses |
| BZ (对抗) | 差（亚克力幽灵点） | L1/L2 过滤后匹配，small_gicp max_dist_sq 适当收紧 |

**small_gicp 分区参数建议** (`localization.yaml`):
```yaml
# BZ 区使用更严格的内点阈值，排斥亚克力幽灵点
max_dist_sq: 1.0 → 0.5   # 在对抗区激活时收紧（需代码支持动态切换）
```

**补充：分区切换的“可执行条件”（避免靠人脑记忆）**  
建议基于 `map` 坐标下的 `base_link` 位置判断所在区域（MC/MF/BZ），按区应用不同的过滤与匹配参数：
```text
pose_map = TF(map->odom) * TF(odom->base_link)
zone = classify(pose_map.x, pose_map.y)   # 区域边界来自建图/场地标定
apply_params(zone)
```
按区参数建议（示例，需结合 bag 回放调参）：
- MF：默认（追求精度）
- MC：更依赖先验（提高 `num_yaw_hypotheses` / 适当放宽 `kidnap_fitness_threshold`）
- BZ：更强 outlier 剔除（更小 `max_dist_sq` + 开启亚克力过滤 L1/L2/L3）

#### I6. 全链路性能 Profile

**必须在实际算力平台完成**，输出以下 KPI：

- Point-LIO CPU 峰值 / 平均占用（核数）
- small_gicp 匹配延迟（ms/帧）
- 全局重定位耗时（触发到接受，ms）
- TF 链路端到端延迟（point cloud → nav2 goal receive）

若 Point-LIO + small_gicp 峰值 CPU > 80%，优先下调 `filter_size_surf`（0.2→0.3）再检查 `ivox_grid_resolution`（当前 2.0，MID-360 场地可用 1.5）。

**建议补充“验收阈值”（避免只测不判）**：
- 局部配准（2Hz）：单次配准耗时 `< 200ms`（留出余量）
- 全局重定位：触发到接受 `< 1500ms`（重试区快速通道目标 `< 500ms`）
- map→odom 稳定性：正常运行时 TF 不出现肉眼可见跳变；开启 BZ 过滤后跳变频率显著下降

### P2 — 有余力时完成

#### I7. 动态 KFS 配准降权

视觉识别模块确认 KFS 位置后，将坐标传递给 localization，对该区域点云配准权重从 1.0 降至 0.1。需增加模块间通信接口。

#### I8. 轮速/外置 IMU 短时兜底

在 LiDAR 点云质量短时下降（幽灵点触发配准跳变）时，用 `rc26_merge_odom` 的轮速+外置 IMU 维持 1–2s 可控轨迹，等待 LiDAR 恢复。

#### I9. 武馆区建图特征增强

建图阶段在 MC 区放置临时反光标记物（如反光球），增加 Zone 1 点云密度。比赛时可保留这些标记（不违规），辅助实时定位。

## 传感器拓扑与标定/同步清单（工程可行性必补）

**拓扑（推荐统一 TF：map → odom → base_link → livox_frame）**：
```text
MID-360 点云+IMU
  └─ Point-LIO
      ├─ /state_estimation (里程计)
      └─ /cloud_registered (配准点云)
            └─ rc26_odom_interface
                ├─ /odom (odom→base_link)
                └─ /registered_scan (odom系点云)
                      └─ rc26_localization
                          └─ TF(map→odom)
```

**标定/同步（最小交付物）**：
- 时间：确认 `LiDAR↔IMU time offset`，记录到 `common.time_diff_lidar_to_imu`（静止/匀速/急转三种工况回放验证）。
- 单位：确认 IMU 输出单位，设置 `mapping.acc_norm`（1.0 或 9.81）；检查 `satu_acc/satu_gyro` 与传感器规格一致。
- 外参：`mapping.extrinsic_T/R` 与 URDF 静态 TF 一致；赛前建议固定 `extrinsic_est_en: false`，避免在线估计引入漂移。
- 同步门限：`odom_interface.max_time_diff_sec` 建议从 `0.2` 逐步收紧到 `0.05~0.1`，并统计丢帧率，找到“既不同步崩溃也不大量丢帧”的甜点。

## 明确不做的事

| 方案 | 拒绝理由 |
|------|---------|
| 替换为 Fast-LIO2 | CPU 收益 10–15%，失去碰撞鲁棒性，重新集成测试成本不值 |
| 引入 FAST-LIVO2 | 需相机标定、额外算力，与 KFS 视觉模块资源竞争，当前赛季风险过高 |
| 引入 LIO-SAM | MID-360 非重复扫描适配成本极高，12m 小场地回环价值有限 |
