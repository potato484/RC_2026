# RC_2026 前端架构 Fitness 准则

## 1. 目的

本文档讨论当前仓库已经存在的本地前端工具，主要包括 `merlin-bt-visualizer` 和 `src/rc26_topo_nav/sim_viewer` 的架构边界与维护规则。

它的目标不是描述“理想中的在线驾驶舱”，而是约束当前已经存在的本地前端工具，避免它在演化过程中失去边界。

## 2. 前端维护的基本准则

### 2.1 前端必须保持工具属性

- 前端是 `src/` 工作区的消费者，不是生产者。
- 前端可以可视化、解释、编辑、导出，但不能越权定义运行时真相。
- 任何“浏览器直接成为机器人控制入口”的需求，都必须先设计单独的在线适配层。

### 2.2 展示模型和编辑模型不得重新混成一套

- 查看器模型允许做展示增强，例如中文标签、装饰器压缩、子树展开。
- 编辑器模型必须保留可逆语义，例如原始标签、原始属性、真实层级关系。
- 不能为了少维护一套类型，把查看态结构重新拿来当 XML 真源。

### 2.3 解析与序列化必须成对维护

- 任何修改 `editorParser`、`editorProjection`、`editorSerializer` 的改动，都必须一起考虑 round-trip。
- 如果改完只能“看起来能显示”，但不能稳定再导出正确 XML，这个改动不算完成。

### 2.4 UI 组件只消费状态，不拥有业务真源

- `Header`、`Sidebar`、`TreeVisualizer`、`RightPanel`、`EditorRightPanel` 都应消费 store 或 utility 输出。
- 组件内部不应悄悄复制一套 XML 解释逻辑。
- 同一种业务解释不能分散在多个组件里各写一份。

### 2.5 不得伪装成真实在线系统

- 没有真实 ROS2 / WebSocket / API 接入之前，文档、命名和交互都必须明确写“本地模拟”“占位模式”“未接入实机”。
- 不允许因为 UI 上有“实机模式”开关，就把它描述成已经上线的在线驾驶舱。

### 2.6 本地文件读取边界必须明确

- 当前前端依赖 `vite` 开发态对上一级目录 XML 的读取能力。
- 这是一种本地工程开发便利，不是通用部署协议。
- 如果未来要脱离当前仓库目录结构部署，必须重新设计数据输入边界。

### 2.7 在线化必须新增 adapter boundary

- 如果未来要接实时状态流，应该新增单独的 adapter 层，例如：
  - 行为树运行时快照适配层
  - ROS2 -> WebSocket 转换层
  - 权限和持久化服务层
- 不允许让 React 页面直接耦合底层 ROS2 细节。
- 当前 `src/rc26_topo_nav/scripts/topo_sim_server.py` 就是一个允许存在的本地 adapter 例子：它负责把 topo 图、world 几何和只读 ROS 状态转换成浏览器消费模型，但不拥有运行时导航权威。

## 3. 当前项目的前端规则

### 3.1 `merlin-bt-visualizer` 和 `src/rc26_topo_nav/sim_viewer` 都不是自研“后端”

- 它们只消费仓库真源、仿真 world 或 adapter 输出。
- 它们都不拥有机器人控制权。
- 它们不能替代 `rc26_visualization`、`rc26_decision`、`rc26_topo_nav` 或其他 ROS2 包的运行时职责。

### 3.2 查看模式只负责看，不负责回写真源

- 查看模式的数据结构可以服务于布局和交互。
- 但查看模式的数据结构不能被当作最终导出真源。

### 3.3 编辑模式必须保住可逆语义

- 新增节点类型、属性能力或树结构操作时，优先修改编辑语义模型。
- 只有编辑语义稳定后，才投影到画布。

### 3.4 模拟执行器只用于演示

- `App.tsx` 里的执行器只能用于本地演示、UI 联调、交互说明。
- 它不是机器人运行时的行为树执行器，不得和真实决策链混淆。

### 3.5 三维 topo viewer 只做观测和离线回放

- `src/rc26_topo_nav/sim_viewer` 可以做完整 3D mesh 渲染、路径回放和只读 live 观察。
- A* 真正的搜索逻辑仍以 `rc26_topo_nav` C++ planner + `planner_trace_cli` 为准，不允许在前端里复制一套“更真实”的规划真源。
- RRT / DWA 在当前实现里是本地仿真算法，它们输出的是同一套 viewer 帧结构，不改变 ROS2 运行时契约。
- 场景完整几何用于渲染，不等于所有 mesh 面都自动变成规划障碍；碰撞 keep-out 的选择仍然属于 adapter / 算法层职责。

## 4. 前端 Fitness Function

### 4.1 工具属性检查

- 问题：这次改动是否让前端开始承担运行时权威职责？
- 通过标准：前端仍然只是消费和编辑工具。

### 4.2 查看态/编辑态分离检查

- 问题：这次改动是否把展示模型重新当成编辑真源？
- 通过标准：展示链路和编辑链路仍然清晰分离。

### 4.3 Round-Trip 检查

- 问题：XML 经编辑解析、投影、导出后，语义是否仍然可逆？
- 通过标准：编辑器 round-trip 行为没有被破坏。

### 4.4 无隐式联机耦合检查

- 问题：这次改动是否偷偷引入了未声明的网络依赖或运行时假设？
- 通过标准：联机能力要么明确设计、要么明确不存在。

### 4.5 能力描述真实性检查

- 问题：文档和 UI 是否准确描述了前端当前能力边界？
- 通过标准：没有把本地模拟功能说成实机在线能力。

## 5. 前端最终立场

对当前仓库，前端的正式立场应当是：

- `merlin-bt-visualizer` 是本地工程工具
- `src/rc26_topo_nav/sim_viewer` 也是本地工程工具
- 它们的当前核心价值分别是“看 XML、改 XML、演示 XML”和“看 topo 场景、看路径、看规划过程”
- 它们都不是在线机器人后端
- 它们都不是运行时控制面
- 如果以后要在线化，必须单独设计 adapter 架构
