# rc26_xhu_viewer 瘦身执行方案

## 1. 文档定位

这份文档是对 [思考.md](/home/potato/RC_2026/docs/backend/archive/rc26_xhu_viewer/思考.md) 的落地版补充。

它不再回答“要不要瘦身”，而是回答：

- 先做哪一步最值
- 哪些改动能马上降低机器人端资源占用
- 哪些改动会牵涉包拆分和依赖重组
- 哪些改动风险过高，不应放在第一阶段

本文档默认遵守以下约束：

- `rc26_xhu_viewer` 仍然是操作员语义聚合边界
- `viewer` 和 Web adapter 继续保持工具属性
- 机器人端首先追求稳定和资源回收，而不是追求目录看起来最干净

## 2. 最终目标

目标不是“把 `src/rc26_xhu_viewer` 目录删小”，而是把当前能力收敛成 3 个更符合真实链路的层次：

### 2.1 机器人最小常驻层

- 默认随 bringup 启动
- 不依赖 GUI
- 不要求图形环境
- 负责发布：
  - `r2/xhu_viewer/summary`
  - `r2/xhu_viewer/operator_status`
  - `r2/xhu_viewer/events`

### 2.2 可选 RViz 调试层

- 只在工程调试或带屏值守时启动
- 不作为机器人默认常驻负担
- 继续承载 `.rviz` 预设和少量必要的 GUI 壳层定制

### 2.3 可选 Web 工具层

- 用于工程分析、回放、现场辅助观察
- 不是整车 bringup 的默认常驻进程
- 保持只读消费者身份

## 3. 现状到目标之间的主要阻塞

### 3.1 当前 `rc26_xhu_viewer` 包把 4 类东西绑在了一起

- 状态聚合
- RViz GUI 壳层
- pluginlib 骨架库
- Web adapter 与前端资源

这会导致两个问题：

- 机器人最小运行时被迫背上 GUI 和工具链资产
- 任意一个方向变化都会把整个包拖进重编译和再验证

### 3.2 当前主 bringup 已经具备“先 headless”的基础条件

已有事实：

- `visualization_backend:=rc26_xhu_viewer | none`
- `visualization_status_enable:=true | false`
- `status_node` 与 GUI viewer 独立装配
- 无 DISPLAY 时 GUI 会自动跳过

这意味着不需要先做大重构，就可以先回收一大块运行时资源。

### 3.3 旧调试流里的 `rviz2` 直接引用已完成迁移

当前落地结果：

- `src/rc26_point_lio/launch/point_lio.launch.py` 已收敛为纯 headless 入口
- `src/rc26_bringup/launch/odometry.launch.py` 已改为 include `rc26_xhu_viewer/launch/viewer.launch.py`

这意味着至少这两条历史调试链已经不再直接拉起 `rviz2`，后续是否继续收缩 vendor 工作区可以在更清晰的前提下再评估。

### 3.4 当前默认 `.rviz` 预设未使用 `rc26_xhu_viewer_plugins`

这说明：

- 插件库不是默认主链必需件
- 它更适合被做成可选构建项或独立调试包

这给了瘦身一个很好的切入点。

## 4. 分阶段策略

## 4.1 P0：先回收机器人端默认运行时资源

### 4.1.1 目标

不改大边界，不做大拆包，优先让机器人默认运行时更轻。

### 4.1.2 建议动作

1. 明确引入“机器人默认 headless”的推荐口径
2. 把 `visualization_status_enable:=true` 保持为默认
3. 把 GUI viewer 从“默认开”收敛为“显式按需开”
4. 给 bringup 增加更清晰的 profile 语义，而不是继续依赖 `use_rviz + visualization_backend` 的历史兼容组合

建议至少形成以下口径之一：

- `visualization_profile:=headless`
- `visualization_profile:=operator_gui`
- `visualization_profile:=engineering_gui`
- `visualization_profile:=diagnostic_gui`

或者保持现有参数，但在默认值和 README 上明确：

- onboard 默认：`visualization_backend:=none visualization_status_enable:=true`
- 带屏调试：`visualization_backend:=rc26_xhu_viewer visualization_layout:=...`

### 4.1.3 主要收益

- 机器人端 CPU / 内存 / GPU 立刻减负
- 不影响 `r2/xhu_viewer/*` 的诊断语义输出
- 不影响 `rc26_decision`、`rc26_topo_nav`、`rc26_terrain` 等上游模块对可视化聚合语义的下游消费

### 4.1.4 需要改的文件

- `src/rc26_bringup/launch/bringup.launch.py`
- `docs/backend/archive/rc26_bringup/README.md`
- `docs/backend/archive/rc26_xhu_viewer/README.md`
- 相关启动文档，如 `导航启动.md`、`重定位启动.md`、`建图启动.md`

### 4.1.5 风险

- 现场使用者如果默认依赖车端 GUI，会感知到使用方式变化
- 需要同步文档，避免“默认 headless”与旧口径冲突

### 4.1.6 验证

1. `visualization_backend:=none visualization_status_enable:=true` 时，确认 `r2/xhu_viewer/*` 仍然持续发布
2. `visualization_backend:=rc26_xhu_viewer` 时，确认 GUI 仍可正常启动
3. 无图形环境时，bringup 不应报错退出，只应跳过 GUI

## 4.2 P0.5：把默认未用插件能力改成可选构建

### 4.2.1 目标

在不拆包的前提下，先让默认构建更瘦。

### 4.2.2 建议动作

在 `rc26_xhu_viewer/rc26_xhu_viewer/CMakeLists.txt` 引入显式开关，例如：

- `BUILD_XHU_VIEWER_GUI`
- `BUILD_XHU_VIEWER_PLUGINS`
- `BUILD_XHU_VIEWER_WEB_TOOLS`

其中更值得先做的是：

- `BUILD_XHU_VIEWER_PLUGINS`
- `BUILD_XHU_VIEWER_WEB_TOOLS`

因为当前默认 `.rviz` 预设并不依赖自定义插件库。

### 4.2.3 推荐收口方式

- `status_core + status_node` 默认总是构建
- `rc26_xhu_viewer_plugins` 默认可关
- `viewer/`、`scripts/rc26_xhu_viewer_server.py`、`web/` 相关安装默认可关

### 4.2.4 主要收益

- 减少默认构建时间
- 减少 install 目录体积
- 避免机器人最小部署携带不必要的 Web 前端和插件骨架

### 4.2.5 需要改的文件

- `src/rc26_xhu_viewer/rc26_xhu_viewer/CMakeLists.txt`
- `src/rc26_xhu_viewer/rc26_xhu_viewer/package.xml`
- `docs/backend/archive/rc26_xhu_viewer/README.md`

### 4.2.6 风险

- 如果有人手工加载了 `rc26_xhu_viewer_plugins`，默认关闭会改变行为
- 需要文档明确“哪些能力属于可选构建”

### 4.2.7 验证

1. 关闭插件和 Web 工具后，`rc26_xhu_viewer_status_node` 必须仍可独立编译和运行
2. GUI 壳层若保留，应仍能加载当前 6 份 `.rviz` 预设
3. 文档里必须明确“默认构建不再包含哪些能力”

## 4.3 P1：拆出机器人最小可视化运行时包

### 4.3.1 目标

把“操作员语义聚合”从 GUI 和工具链里剥离出来，形成最小常驻单元。

### 4.3.2 建议目标形态

建议拆成至少两个包：

1. `rc26_xhu_viewer_status`
内容：
- `xhu_viewer_status_core`
- `rc26_xhu_viewer_status_node`
- `config/xhu_viewer_status.yaml`

2. `rc26_xhu_viewer_rviz` 或继续保留 `rc26_xhu_viewer`
内容：
- GUI 壳层
- `.rviz` 预设
- 需要的 RViz 定制能力

如果希望进一步清晰，还可以追加：

3. `rc26_xhu_viewer_tools_web`
内容：
- `rc26_xhu_viewer_server.py`
- `viewer/`
- `web/`

### 4.3.3 这么拆的原因

这比继续把所有能力塞进一个包更符合真实变化原因：

- `status` 变化跟机器人技术语义有关
- `rviz` 变化跟 GUI 壳层与布局有关
- `web tools` 变化跟工程工具链有关

### 4.3.4 主要收益

- 机器人最小部署单元显著变轻
- `rc26_bringup` 更容易清晰声明依赖
- 未来 Web 工具链可以单独演进，不拖机器人端运行时

### 4.3.5 需要改的文件

- `src/rc26_xhu_viewer/rc26_xhu_viewer/CMakeLists.txt`
- `src/rc26_xhu_viewer/rc26_xhu_viewer/package.xml`
- 新包目录及其 `package.xml` / `CMakeLists.txt`
- `src/rc26_bringup/launch/bringup.launch.py`
- `docs/backend/archive/rc26_xhu_viewer/README.md`
- `docs/backend/archive/rc26_bringup/README.md`
- 如新增包，需要对应新增 `docs/backend/archive/<pkg>/README.md`

### 4.3.6 风险

- 包拆分会牵涉 launch、安装路径、ament index 查找路径
- 若文档不同步，后续协作者很容易误判哪个包才是权威

### 4.3.7 验证

1. `rc26_xhu_viewer_status` 包独立 build 成功
2. bringup 只启 `status` 时功能完整
3. GUI 包单独 build 成功，并可按需启动
4. Web 工具包若单独构建/部署，不影响机器人主链

## 4.4 P1.5：清理旧调试流里的 `rviz2` 直接引用

### 4.4.1 目标

先把残留入口迁走，再谈 `rviz2` 的去留。

### 4.4.2 建议动作

逐个处理当前已知直接引用：

- `src/rc26_point_lio/launch/point_lio.launch.py`
- `src/rc26_bringup/launch/odometry.launch.py`

当前已完成的实际落地：

1. `point_lio.launch.py` 保留兼容参数 `rviz`，但不再直接启动 `rviz2`
2. `odometry.launch.py` 的 `odometry_use_rviz:=true` 现在改为启动 `rc26_xhu_viewer`
3. 相关 README 与调试文档已同步更新

可选方向：

1. 继续保留 `rviz2`，但明确它只是历史调试入口
2. 改为使用 `rc26_xhu_viewer` 的更轻量预设
3. 改成纯 headless 默认，调试时手工起 viewer

### 4.4.3 主要收益

- 后续是否删除 `rviz2` 会更清晰
- 减少“主链已切走，但侧链还偷偷依赖旧入口”的混乱

### 4.4.4 风险

- 某些旧调试手册和现场习惯会受影响
- 需要一起改 README 和启动文档

## 4.5 P2：重新评估是否保留本地 RViz vendor 工作区

### 4.5.1 目标

这是最终态讨论，不应作为第一阶段动作。

### 4.5.2 适用前提

只有在满足以下条件后，才建议进入 P2：

1. `status` 已与 GUI 拆开
2. 旧 `rviz2` 直接引用已清理
3. 当前仍然需要的 RViz 定制点已被重新评估
4. 已明确本地 `rviz_common` patch 是否还能接受继续维护

### 4.5.3 两条可选方向

#### 方向 A：继续保留本地 fork，但只保留必要子集

可考虑：

- 去掉 `rviz_visual_testing_framework`
- 去掉 `rviz_rendering_tests`
- 评估是否还要保留 `rviz2`

这条路的特点是：

- 改动相对保守
- 仍保留 `rviz_common` 本地 patch
- 仍需长期承担 fork 维护成本

#### 方向 B：逐步退出本地 fork，回归系统 RViz 依赖

可考虑：

- 不再把整套 RViz upstream 放在主工作区 `src/`
- 改为依赖系统安装的 `rviz2 / rviz_common / rviz_rendering`
- RC26 只保留自己的状态聚合、预设配置和少量适配层

这条路的特点是：

- 长期维护成本最低
- 但前期改造和兼容验证成本最高
- 需要重新处理当前 `rviz_common` 本地 patch 提供的能力

### 4.5.4 结论

P2 应该被视为：

- **长期结构优化**

而不是：

- **第一步资源减负手段**

## 5. 不建议优先做的事情

## 5.1 不建议一上来直接删除 `rviz_common / rviz_rendering / rviz_default_plugins`

原因：

- 当前 GUI 壳层和默认 `.rviz` 预设还直接依赖这些能力
- 这样做会把低风险资源优化问题直接升级成高风险架构重写

## 5.2 不建议为了瘦身把操作员语义聚合散回各业务包

原因：

- 会破坏 `rc26_xhu_viewer` 作为操作员语义聚合边界的职责
- 会让状态语义重新碎片化

## 5.3 不建议先重写 Web viewer 或 Babylon 前端

原因：

- 它们不是当前机器人端默认运行时的主要负担
- 先重写前端，并不能立刻解决实机资源占用问题

## 6. 推荐实施顺序

### 6.1 第一轮

- 调整 bringup 默认口径，形成默认 headless
- 保留 `visualization_status_enable:=true`
- 补齐相关 README 和启动文档

### 6.2 第二轮

- 给 `rc26_xhu_viewer` 增加可选构建开关
- 默认关闭未进入主链的插件和 Web 工具安装

### 6.3 第三轮

- 拆出 `status` 最小包
- 把 GUI 与 Web 工具链移出最小部署单元

### 6.4 第四轮

- 清理 `rviz2` 旧调试引用
- 再决定是否继续缩减 vendor 工作区

## 7. 建议的验证矩阵

### 7.1 P0 验证

```bash
MAKEFLAGS='-j2 -l2' colcon build --executor sequential --parallel-workers 1 --packages-select rc26_bringup rc26_xhu_viewer
```

现场验证：

1. `visualization_backend:=none visualization_status_enable:=true`
2. `visualization_backend:=rc26_xhu_viewer visualization_layout:=operator`
3. 无图形环境时 bringup 正常继续

### 7.2 P1 验证

```bash
MAKEFLAGS='-j2 -l2' colcon build --executor sequential --parallel-workers 1 --packages-select <新拆分的 status/gui/web 包>
```

验证点：

1. `status` 包独立 build 成功
2. GUI 包独立 build 成功
3. Web 工具包独立 build 成功
4. bringup 的依赖方向没有逆流

### 7.3 P2 验证

除包级 build 外，还需要确认：

1. 当前 `.rviz` 预设能否继续正常加载
2. 当前白名单和中文菜单能力是否仍存在或已有替代
3. 调试 launch 是否还有残留 `rviz2` 依赖

## 8. 最终执行建议

如果只允许我给一个最现实的执行判断，那就是：

### 8.1 先做

- `P0 默认 headless`
- `P0.5 可选构建`

这是当前收益最大、风险最低、最符合“更快、更省资源、更贴合真实链路”的做法。

### 8.2 再做

- `P1 status/gui/web 拆分`

这是从“减负”走向“结构健康”的关键一步。

### 8.3 最后再决定

- `P2 是否退出本地 RViz fork`

这应该建立在前两阶段已经稳定落地的前提上，而不应直接一步到位。
