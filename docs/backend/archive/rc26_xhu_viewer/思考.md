# rc26_xhu_viewer 瘦身思考

> 注：本文档保留的是独立 `rc26_xhu_viewer` 包时期的阶段性分析。当前真实实现已经进一步收口为 `rc26_xhu_viewer_status + rviz2`，独立 GUI 包已退役；下文涉及 `visualization_backend:=rc26_xhu_viewer`、`rc26_xhu_viewer/launch/viewer.launch.py` 或独立 viewer 进程的描述都只代表历史阶段，不再代表当前默认启动口径。阅读当前实现请优先看 `rviz2/README.md` 与 `瘦身执行方案.md`。

## 1. 目的

这份文档只讨论 `src/rc26_xhu_viewer` 这棵目录树的瘦身方向，目标不是“为了看起来更小而删代码”，而是同时满足：

- 更贴近 R2 当前真实链路
- 减少机器人端默认运行时资源占用
- 减少工作区构建、安装和维护成本
- 尽量不打破 `docs/fitness/` 已定义的边界

这里要先分清 3 类成本：

- **运行时成本**：启动进程后的 CPU、内存、GPU、图形栈占用
- **构建/安装成本**：colcon 编译时间、安装体积、部署体积
- **维护成本**：本地 fork 面、上游同步难度、包边界混乱

这 3 类成本不是一回事。很多 vendor 目录的存在本身不会拖慢机器人运行，但会拖慢构建、增大安装体积，并放大后续维护成本。

## 2. 当前事实

### 2.1 当前目录树实际由 9 个 ROS2 包组成

`src/rc26_xhu_viewer` 当前包含：

- `rc26_xhu_viewer`
- `rviz2`
- `rviz_assimp_vendor`
- `rviz_common`
- `rviz_default_plugins`
- `rviz_ogre_vendor`
- `rviz_rendering`
- `rviz_rendering_tests`
- `rviz_visual_testing_framework`

这意味着当前并不是“一个 RC26 viewer 包”，而是“RC26 运行时包 + 一整套上游 RViz 工作区副本”。

### 2.2 bringup 当前把 GUI viewer 和 status node 分开装配

`rc26_bringup` 里：

- `visualization_backend` 已收口为 `rc26_xhu_viewer | none`
- `rc26_xhu_viewer_status_node` 独立装配
- GUI viewer 只有在 `visualization_backend:=rc26_xhu_viewer` 且存在图形环境时才启动

这说明当前链路已经天然支持一个重要方向：

> 保留 `status_node`，但默认不在机器人端启动重型 GUI。

这也是最现实、收益最大的运行时减负切入点。

### 2.3 当前 6 份 `.rviz` 预设没有加载任何 `rc26_xhu_viewer/*` 自定义插件

当前仓库内的：

- `navigation_operator.rviz`
- `navigation_engineering.rviz`
- `navigation_diagnostic.rviz`
- `slam_operator.rviz`
- `slam_engineering.rviz`
- `slam_diagnostic.rviz`

实际加载的是：

- `rviz_default_plugins/*`
- `grid_map_rviz_plugin/GridMap`

没有任何一份默认预设直接加载：

- `rc26_xhu_viewer/* Panel`
- `rc26_xhu_viewer/* Display`

这说明一个非常关键的事实：

> `rc26_xhu_viewer_plugins` 当前更像“预留能力”或“手工加载能力”，不是默认主链的运行时依赖。

### 2.4 当前有明确本地分叉维护成本的 vendor 包，主要是 `rviz_common`

目前可确认的本地改动集中在 `rviz_common`：

- `VisualizationFrame::initMenus()` / `initToolbars()` 允许覆写
- `VisualizationManager` 增加 `setDisplayFactory()`
- `display_factory.hpp` 对外公开
- FPS 状态栏中文化

这部分支撑了：

- `RC26XhuViewerFrame`
- Display 白名单
- 中文菜单/工具栏

而其他 vendor 包目前基本保持上游形态，更多是“整包带进来”而不是“被深度本地改造”。

### 2.5 `rviz2` 对当前主 bringup 不是主链，旧调试流的直连入口也已迁移

当前主 bringup 已经不再以 `rviz2` 为默认可视化入口，实际入口是 `rc26_xhu_viewer`。

此前旧调试流里存在过两处直接起 `rviz2` 的 launch：

- `src/rc26_point_lio/launch/point_lio.launch.py`
- `src/rc26_bringup/launch/odometry.launch.py`

当前这两处已经迁移为：

- `point_lio.launch.py` 只保留纯 headless Point-LIO 入口
- `odometry.launch.py` 改为通过 `rc26_xhu_viewer/launch/viewer.launch.py` 装配调试 GUI

所以当前判断变成：

- 对 **R2 主链** 而言，`rviz2` 是冗余入口
- 对 **这两条旧调试流** 而言，`rviz2` 已不再是直接依赖

### 2.6 Web viewer 和 adapter 当前属于工程工具，而不是 bringup 默认运行时

`rc26_xhu_viewer` 包内还包含：

- `scripts/rc26_xhu_viewer_server.py`
- `viewer/` React + Babylon 前端

它们当前不属于 bringup 默认主链的 GUI 后端，只是本地工程工具。按 `docs/frontend/` 和 `docs/fitness/architecture_fitness_frontend/README.md` 的口径，它们应该继续保持消费者身份，而不是反向吞掉运行时权威。

这意味着它们更适合被视为：

- 可选工具链
- 工程分析能力
- 非机器人端默认部署物

而不是和 `status_node`、RViz 核心壳层一起强绑定在一个最小部署单元里。

## 3. 资源到底耗在哪

## 3.1 机器人端运行时最大的成本，不是 vendor 目录本身，而是 GUI 进程

如果只讨论机器人启动后的资源占用，最大头通常不是源码目录，而是：

- Qt + Ogre 图形栈
- `rc26_xhu_viewer` GUI 进程本身
- RViz 渲染窗口、材质、纹理、点云显示
- 图形环境带来的 GPU / 显存 / 合成器成本

所以：

- 删除 `rviz_rendering_tests` 不会直接让机器人跑得更快
- 让 bringup 默认不拉 GUI，通常会马上带来明显运行时收益

## 3.2 构建和部署体积的最大成本，是整套 vendor 工作区 + 未使用插件

如果讨论构建时间、安装体积、镜像体积，成本主要来自：

- 一整套 RViz vendor 包都在 `src/` 内参与工作区管理
- `rviz_visual_testing_framework` / `rviz_rendering_tests` 这类测试包仍然占目录和依赖视野
- `rc26_xhu_viewer_plugins` 会编译 14 个 Panel、5 个 Display、SQLite 历史库、Web panel 基础设施
- `viewer/` 前端资源也一起跟着 ROS 包安装

这些东西不一定都在运行时常驻，但会放大：

- 全量构建时间
- install 目录体积
- 部署包大小
- 上游同步复杂度

## 3.3 维护成本最大的点，是“可视化聚合边界”和“RViz fork”绑在一个包里

当前一个 `rc26_xhu_viewer` 包里同时承载了：

- GUI 壳层
- 状态聚合
- 插件骨架
- 本地历史库
- Web adapter
- Web 前端

这虽然短期方便，但长期会让 3 种变化原因绑在一起：

- 机器人端状态语义变化
- GUI 与 RViz 壳层变化
- 工程工具链变化

这和 `docs/fitness/architecture_fitness_ros2_workspace/README.md` 里的“每个包应尽量只有一个主要职责和一个主要变化原因”并不完全一致。

## 4. 当前可以判定的冗余层次

### 4.1 对机器人默认运行时明确冗余

- `rviz_visual_testing_framework`
- `rviz_rendering_tests`

它们属于上游测试资产，不应该进入机器人最小运行时思路。

### 4.2 对默认 `.rviz` 主链当前明显富余

- `rc26_xhu_viewer_plugins` 中绝大多数 Panel / Display 骨架
- `web_panel_base` / `web_bridge` 相关内嵌 Web 基础设施

原因不是“它们不能存在”，而是：

- 默认预设并没有加载它们
- 当前主 bringup 也不依赖它们形成核心可视化闭环

这部分属于“当前实现预留能力 > 当前主链实际使用”的典型富余。

### 4.3 对主 bringup 基本冗余，但对旧调试链仍有遗留用途

- `rviz2`

它不再是主 bringup 的默认入口，但仍被少数 launch 文件直接引用，不能不迁移就直接删。

### 4.4 当前不宜简单删除的核心依赖

- `rviz_common`
- `rviz_rendering`
- `rviz_ogre_vendor`
- `rviz_assimp_vendor`
- `rviz_default_plugins` 的当前已用子集

原因很直接：

- `rc26_xhu_viewer` GUI 壳层直接依赖 `rviz_common`
- 当前默认 `.rviz` 预设大量依赖 `rviz_default_plugins`
- 渲染链离不开 `rviz_rendering + Ogre + assimp`

## 5. 瘦身应遵守的原则

### 5.1 先减默认运行时，再减源码树

如果目标是“更快、更省资源”，优先级应当是：

1. 先让机器人端默认少起重型 GUI
2. 再处理构建和目录层面的冗余
3. 最后才考虑彻底去掉本地 RViz fork

因为第 1 步的收益最大，风险也最低。

### 5.2 保留 `rc26_xhu_viewer` 的语义聚合边界，但不必强求单一 ROS 包

按架构文档，`rc26_xhu_viewer` 的本质职责是：

> 把定位、控制、地形、keepout、机构、导航运行态聚合成操作员语义。

这个边界应该保留，但不等于必须把以下内容永远绑成一个包：

- 状态聚合
- RViz GUI
- Web adapter
- Web 前端

更合理的方向是：

- 保留“同一可视化域”
- 允许拆成更轻薄、变化原因更单一的几个包

### 5.3 不要为了瘦身而把操作员语义再打散回各业务包

瘦身不应走向另一个极端：把 `operator_status`、事件聚合、告警规则重新散回 localization、terrain、controller、decision 各处。

否则节省的是一点目录体积，增加的是长期诊断混乱成本。

## 6. 推荐的分阶段路线

## 6.1 第一阶段：低风险减负，优先拿运行时收益

这一阶段的原则是“不改主语义，不动大边界”。

建议方向：

- 为机器人端引入更明确的 `headless / competition / onboard` 启动口径
- 让这类口径默认：
  - `visualization_backend:=none`
  - `visualization_status_enable:=true`
- 保留 `rc26_xhu_viewer_status_node`
- 把 GUI viewer 改成显式按需启动，而不是车端默认带着跑

这一步的收益：

- 运行时 CPU / 内存 / GPU 占用立刻下降
- 不影响 `r2/xhu_viewer/*` 诊断总线
- 不影响上层基于状态语义做判断

这一步的风险：

- 操作员如果习惯“车端自带 GUI”，使用方式需要同步调整

因此更稳妥的做法不是直接粗暴改全局默认，而是先引入明确 profile，再逐步收敛默认值。

## 6.2 第二阶段：把“默认未用能力”从最小交付单元里拆出去

当前最值得优先处理的是：

- `rc26_xhu_viewer_plugins`
- `viewer/`
- `rc26_xhu_viewer_server.py`

建议方向：

- 把 `status_core + status_node` 独立成轻量包
- 把 RViz GUI 壳层独立成可选 GUI 包
- 把 Web adapter + 前端独立成工程工具包

这样之后，最小机器人部署单元只保留：

- 语义聚合
- 结构化状态输出

而不是再强绑：

- Qt GUI
- pluginlib 骨架库
- Web 前端资源

这是当前最符合“更适配当前项目链路”的中期目标。

## 6.3 第三阶段：重新评估本地 RViz fork 是否还值得保留

这是收益很大、但风险也最高的一步。

当前继续保留整套 RViz vendor 的主要价值在于：

- `RC26XhuViewerFrame`
- 中文菜单/工具栏
- Display 白名单
- 局部 GUI 壳层可控

但要看到另一面：

- 当前默认 `.rviz` 预设并没有加载任何自定义 `rc26_xhu_viewer/*` 插件
- `rviz2` 已不是主 bringup 入口
- 维护本地 fork 的长期成本会持续存在

所以后续要认真判断：

> 当前还是否真的需要继续维护一整套本地 RViz 源码副本？

如果答案是否定的，那么更激进但更干净的方向是：

- 改为依赖系统 `rviz2` / `rviz_common` / `rviz_rendering`
- 本地只保留：
  - `rc26_xhu_viewer_status`
  - 预设 `.rviz` 配置
  - 必要 launch
  - 少量适配脚本

但这一步必须先正面接受一个事实：

- 需要放弃或替代当前 `rviz_common` 本地 patch 带来的定制能力

因此它不能作为第一步。

## 7. 我认为最合理的目标形态

如果只从“当前 R2 实际链路 + QCS8550 资源约束 + 后续维护成本”出发，我更倾向于以下目标形态：

### 7.1 机器人端最小可视化域

- 一个轻量 `status` 聚合包
- 默认随 bringup 启动
- 负责发布：
  - `r2/xhu_viewer/summary`
  - `r2/xhu_viewer/operator_status`
  - `r2/xhu_viewer/events`

### 7.2 可选 RViz 工具链

- 只在工程调试或带屏操作时启动
- 不作为机器人默认运行时负担
- 默认只保留当前确实使用的预设和默认插件依赖

### 7.3 可选 Web 工具链

- 保持工程工具身份
- 继续通过 adapter 消费运行时状态
- 不再和机器人最小部署单元强绑定

## 8. 具体保留/收缩建议

### 8.1 当前建议保留

- `rc26_xhu_viewer_status_core`
- `rc26_xhu_viewer_status_node`
- 当前 `.rviz` 预设
- `rviz_common`
- `rviz_rendering`
- `rviz_ogre_vendor`
- `rviz_assimp_vendor`
- 当前主链实际用到的 `rviz_default_plugins`

### 8.2 当前建议优先收缩

- `rviz_visual_testing_framework`
- `rviz_rendering_tests`
- `rc26_xhu_viewer_plugins` 中默认预设未使用的骨架能力
- `viewer/` 与 `rc26_xhu_viewer_server.py` 在机器人最小部署中的地位

### 8.3 当前不建议直接硬删

- `rviz2`

虽然 `src/rc26_point_lio/launch/point_lio.launch.py` 与 `src/rc26_bringup/launch/odometry.launch.py` 这两处旧调试入口已经完成迁移，但是否继续删除 `rviz2` 仍应建立在更完整的 vendor 评估之上，而不是只看到这两处引用消失就立即硬删。

## 9. 验证建议

如果后续真的开始做瘦身，我建议每一步至少验证以下几项：

1. `visualization_backend:=none visualization_status_enable:=true` 时，bringup 是否仍能稳定发布 `r2/xhu_viewer/*`
2. 默认导航链和纯建图链在 headless 模式下是否功能不回退
3. 现有 `.rviz` 预设是否确实未依赖 `rc26_xhu_viewer_plugins`
4. `point_lio.launch.py`、`odometry.launch.py` 的 `rviz2` 引用是否已迁移或外部化
5. 包级编译是否仍可用标准命令验证

推荐继续沿用仓库统一口径：

```bash
MAKEFLAGS='-j2 -l2' colcon build --executor sequential --parallel-workers 1 --packages-select <pkg...>
```

## 10. 最终判断

当前 `src/rc26_xhu_viewer` 最值得做的，不是立刻“删掉所有 vendor 包”，而是按收益和风险排序去做：

1. **先让机器人默认运行时摆脱 GUI 负担**
2. **再把 status / GUI / Web 工具链拆成更符合变化原因的交付单元**
3. **最后再决定是否彻底退出本地 RViz fork**

如果反过来，一上来就试图先删 `rviz_common` / `rviz_rendering` / `rviz_default_plugins`，大概率会进入高风险重构，短期不一定更快，反而更容易把当前已经稳定的操作员语义聚合链打散。

对当前项目而言，最现实的瘦身关键词应该是：

- **默认 headless**
- **status 常驻**
- **GUI 可选**
- **Web 工具链外移**
- **减少本地 RViz fork 面**
