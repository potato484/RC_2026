# 视觉推理补充：多模型切换 + 多推理引擎（ONNX Runtime / AidLite）

本文档用于补充 `src/rc26_md/视觉推理.md` 与 `src/rc26_vision/README.md`：在现有 `rc26_vision` 基础上，增加**运行时切换识别模型**能力，并引入可选的 **AidLite 推理引擎**（通过 YAML 配置选择/切换）。

---

## 1. 背景与目标

### 1.1 现状（当前实现）

- `rc26_vision::VisionInferenceManager` 通过 `configure(model_path, class_names, conf_thresh)` 加载单一模型，并由 `start()/stop()` 控制推理线程。
- `rc26_decision` 在启动时创建 `VisionInferenceManager` 写入 BT 黑板（`vision_manager`），并提供 BT 节点：`VisionStart / VisionStop / WaitVisionTarget`。
- 当前不支持在运行中按**任意场景/任务/子树**切换不同模型（例如不同区域、不同目标类型、速度/精度档位切换），也不支持切换推理后端（仅 ONNX Runtime）。

### 1.2 目标（本补充要解决的问题）

1. **多模型切换接口**：在 `rc26_vision` 增加“切换识别模式/模型”的接口，使行为树能够：
   - 在任意行为树子树/任务阶段使用指定模型（武馆/梅林仅是示例，并非限定）；
   - 同一个任务中可按条件切换（例如：先用 `fast` 粗检，失败则切到 `accurate` 复检）；
   - 通过调用“切换模式/模型”或在 `start` 前指定模型完成切换（统一接口模板）。
2. **新增推理引擎（AidLite）**：在保持 ONNX Runtime 现有能力的同时，新增 AidLite 后端（参考 `src/rc26_md/AidLite C++ 接口文档.md`），并支持在 YAML 中配置引擎与模型信息。
3. **仅文档**：本文只定义接口与配置约定，不包含实现代码。

---

## 2. 核心概念：Model Profile（“识别模式”模板）

为支撑“在任意节点切换识别模式”，引入 **Model Profile** 概念：用一个 `model_id`（字符串）标识一组完整的推理配置。这里的 `model_id` 也可理解为 **mode_id / profile_id**（接口模板中建议统一用 `model_id`，但语义是“识别模式”）。

每个 Profile 至少包含：

- **模式标识**：`model_id`（例如 `area_mc`、`area_mf`、`combat_fast`、`combat_accurate`、`kfs_only`、`robot_only` 等；数量不限）
- **推理引擎类型**：`engine`（`onnxruntime` / `aidlite`）
- **模型文件**：`model_path`
- **类别表**：`labels`（内联列表）或 `labels_path`（文件路径）
- **阈值**：`conf_thresh`、可选 `iou_thresh`
- **后端专用字段**：如 AidLite 的 `framework_type / accelerate_type / input_tensor / output_tensors ...`

> 建议：BT/业务侧只依赖稳定的 `model_id`（模板键），不要把文件路径/硬件后端细节写进 BT XML；这些都留在 YAML Profile 内。

### 2.1 常见 Profile 划分方式（示例，数量不限）

- **按区域/阶段**：`area_mc`、`area_mf`、`area_combat`
- **按任务目标**：`detect_robot`、`detect_kfs`、`detect_marker`
- **按速度/精度档位**：`combat_fast` / `combat_accurate`（同任务不同权重/分辨率/阈值）
- **按硬件/后端**：`*_cpu`、`*_dsp`、`*_aidlite`（便于 A/B 测试与降级）

### 2.2 输出契约（重要：避免“换模型后上层读不懂”）

当前 `rc26_decision`/BT 黑板使用的是 `TargetResult` 语义（`vision_has_target / vision_attr_kind / vision_distance_m ...`）。

- 若 Profile 切换仅发生在“同一类任务”（例如都是 YOLO 检测同一套业务属性），则切换是**天然兼容**的。
- 若希望引入“不同任务类型的模型”（例如分割、关键点、OCR、多目标列表），建议采用：
  - **独立的 Manager + 独立黑板键**（推荐，互不干扰），或
  - **扩展统一结果 schema**（需要同步修改上层读取与 BT 节点）。

## 3. `rc26_vision`：模型切换接口设计（文档约定）

### 3.1 需求约束（行为树可用性）

- 切换模型的动作应当是**可控、可观测、可失败但不崩溃**：
  - 传入未知 `model_id` 时，返回失败且保持当前模型不变；
  - 切换过程中更新 `vision_ok` 状态，便于 BT 判断/降级；
  - 行为树侧只需要“切换/指定模型”的最小动作节点，不需要理解推理后端细节。

### 3.2 推荐提供的能力（API 语义）

在 `rc26_vision::VisionInferenceManager` 增加如下“语义级接口”（名称可按工程风格调整，语义保持一致）：

#### A) `selectModel(model_id)`：选择模型（不隐式启动）

- **用途**：在“识别前”指定模型（符合需求 1 的第二种方式）。
- **约束**：若推理线程正在运行，推荐行为：
  - **方案 A（保守）**：拒绝切换并返回失败（要求 BT 先 `VisionStop`）。
  - **方案 B（便捷）**：内部执行 stop→切换→保持 stopped，返回成功/失败。

#### B) `switchModel(model_id, restart_policy)`：切换模型（可选自动重启）

- **用途**：在行为树中仅调用一次动作即可完成“切换识别模式（改变识别模型）”。
- **建议语义**：
  - 若当前正在推理：stop→切换→按 `restart_policy` 决定是否自动 start；
  - 若当前未推理：仅切换。

#### C) `start(model_id?)`：启动时可指定模型

- **用途**：把“切换 + 启动”合并为一次调用（符合需求 1 的第一种方式：在识别前调用指定模型）。
- **建议语义**：
  - `model_id` 为空：沿用当前已选模型；
  - `model_id` 非空：等价于 `switchModel(model_id, restart=true)`。

#### D) （可选）`getActiveModel()`：查询当前模式

- **用途**：诊断/日志/上层状态机使用，便于确认“当前识别模式是否正确生效”。

#### E) （可选）`pushModel(model_id)` / `popModel()`：临时切换（栈式）

- **用途**：在子树内部临时切到另一种识别模式，退出子树后自动恢复（适合嵌套子树）。
- **建议语义**：
  - `pushModel`：保存当前 `model_id` 到栈，再切换到新 `model_id`；
  - `popModel`：恢复到栈顶上一个 `model_id`（若栈空则失败或回退到默认）。

### 3.3 切换策略（性能/时延权衡）

切换模型的实现可采用两类策略（供后续实现选型，配置见第 5 章）：

- **reload（按需加载）**：切换时才加载模型，占用内存小，但切换有加载时延（推荐默认）。
- **preload（启动预加载）**：启动时加载全部 Profile，切换近似 O(1)，但占用内存大。

> 多数任务切换频率低，默认 `reload` 即可；若需要“条件触发频繁切换”（例如 fast/accurate 频繁交替），可考虑 `preload`。

## 4. 行为树（BT）侧使用方式（推荐编排）

### 4.1 模板：显式切换节点 + 启动节点（最清晰，推荐）

在进入任意子树/任务阶段时：

1. `VisionSetModel model_id="..."`（新增 BT Action，`model_id` 为模板键）
2. `VisionStart`

在退出子树/任务阶段时：

- `VisionStop`（可选，取决于是否希望视觉常开）

示例（仅示意，不限定武馆/梅林；任何子树都可套用同一模板）：

```xml
<Sequence name="Any_Task_Sequence">
  <VisionSetModel model_id="some_profile_id"/>
  <VisionStart/>
  <!-- ...本任务业务... -->
  <VisionStop/>
</Sequence>
```

> 推荐把 `model_id` 写成“稳定的模式名”，例如 `combat_fast` 而不是文件名；模型文件路径由 YAML 管理。

### 4.2 模板：在 `VisionStart` 里带可选参数（最省节点）

把“切换 + 启动”合并：

```xml
<VisionStart model_id="some_profile_id"/>
```

当 `model_id` 缺省时沿用当前模型。

> 推荐优先采用方式一：可读性强、失败点清晰；方式二适合追求节点最少的树。

### 4.3 模板：用黑板变量动态选择 `model_id`（更通用）

当同一棵子树需要根据条件选择不同模式（例如 fast/accurate、不同目标类型），可让 BT 从黑板读取 `model_id`：

```xml
<Sequence>
  <VisionSetModel model_id="{vision_model_id}"/>
  <VisionStart/>
  <!-- ... -->
</Sequence>
```

其中 `{vision_model_id}` 由其他节点写入黑板（例如进入任务时设置成 `combat_fast`，失败后改为 `combat_accurate`）。

## 5. 新推理引擎：AidLite（YAML 可配置）

### 5.0 阅读指引（遇到困惑先看这里）

如果在“新增/接入 AidLite 推理引擎”时对任何细节不确定（接口调用顺序、枚举含义、输入输出张量命名、数据类型要求、REMOTE/LOCAL 区别等），优先查看：

- `src/rc26_md/AidLite C++ 接口文档.md`

建议重点关注该文档中的章节：`Config`、`Context`、`Interpreter`、`InterpreterBuilder`、以及 QNN/SNPE 的 float32 输入输出说明与多输出 Tensor 示例。

### 5.1 AidLite 引擎要点（来自接口文档的关键约束）

参考 `src/rc26_md/AidLite C++ 接口文档.md`：

- 典型流程：`Model` + `Config` → `InterpreterBuilder` → `Interpreter::init()` → `load_model()` → `set_input_tensor()` → `invoke()` → `get_output_tensor()` → `destory()`
- 关键枚举：
  - `FrameworkType`：如 `TYPE_QNN236`（也可用 `TYPE_QNN` 表示“最高版本 QNN”，但需注意版本约束）
  - `AccelerateType`：`TYPE_CPU / TYPE_GPU / TYPE_DSP / TYPE_NPU`
  - `ImplementType`：`TYPE_LOCAL`（推荐）/ `TYPE_REMOTE`
- **SNPE/QNN 输入输出数据类型固定 float32**：即使模型是量化，`set_input_tensor()` 传入/`get_output_tensor()` 取回仍按 float32 处理（文档明确说明）。
- QNN YOLO 示例通常存在 **多个输出 Tensor**（示例中 3 个输出：`_326/_364/_402`），需要在配置中明确输出节点名称列表。

### 5.2 引擎选择粒度

建议支持两种配置粒度（二选一即可；推荐按 Profile 粒度更灵活）：

- **全局引擎**：整个 `rc26_vision` 使用同一种 engine（简单，但限制大）
- **按 Profile 选择引擎**：`mc_area` 用 ONNX，`mf_area` 用 AidLite（更符合“分区策略”）

## 6. YAML 配置约定（建议方案）

> 说明：由于多模型与多引擎涉及嵌套结构，建议使用“独立 YAML 配置文件”由上层（如 `rc26_decision`）读取并传入 `rc26_vision`，而不是仅依赖 ROS 参数扁平键值。本文只定义文件内容格式，不限定由谁解析。

### 6.1 顶层结构

- `vision.default_model`：默认 Profile（启动后未显式选择时使用）
- `vision.switch_policy`：`reload` 或 `preload`
- `vision.models`：Profile 列表（map）

### 6.2 Profile 字段（统一字段）

每个 `vision.models.<model_id>` 建议支持：

- `engine`: `onnxruntime` | `aidlite`
- `model_path`: 模型文件路径（onnx / aidlite 后端模型）
- `labels_path` 或 `labels`: 类别表
- `conf_thresh`: 置信度阈值
- `iou_thresh`: NMS IoU 阈值（可选，若后端/实现支持）
- `input_w/input_h`: 输入尺寸（可选，默认 640x640，保持与现有实现一致）

### 6.3 AidLite 专用字段（当 engine=aidlite）

建议放在 `aidlite:` 子块下：

- `framework_type`: `QNN236` / `QNN` / `SNPE2xx` ...（与 AidLite 枚举对应）
- `accelerate_type`: `CPU` / `GPU` / `DSP` / `NPU`
- `implement_type`: `LOCAL` / `REMOTE`（推荐 `LOCAL`）
- `input_tensor`: 输入节点名（示例：`images`）
- `output_tensors`: 输出节点名数组（示例：`["_326","_364","_402"]`）
- `output_layout`: 输出布局标识（例如：`yolov5_multi`），用于选择对应后处理逻辑

### 6.4 示例：多 Profile（区域/任务/档位混用）

```yaml
vision:
  default_model: mc_area
  switch_policy: reload  # reload|preload

  models:
    mc_area:
      engine: onnxruntime
      model_path: "/models/yolo_mc.onnx"
      labels_path: "/models/labels_mc.txt"
      conf_thresh: 0.50
      iou_thresh: 0.45
      input_w: 640
      input_h: 640

    # 同一任务的“速度/精度”档位示例（同模型不同阈值/分辨率，或不同权重文件均可）
    combat_fast:
      engine: onnxruntime
      model_path: "/models/yolo_combat_fast.onnx"
      labels_path: "/models/labels_combat.txt"
      conf_thresh: 0.55
      iou_thresh: 0.45
      input_w: 640
      input_h: 640

    combat_accurate:
      engine: onnxruntime
      model_path: "/models/yolo_combat_accurate.onnx"
      labels_path: "/models/labels_combat.txt"
      conf_thresh: 0.40
      iou_thresh: 0.50
      input_w: 960
      input_h: 960

    # 不同任务目标示例（例如只关心 KFS/方块）
    detect_kfs:
      engine: onnxruntime
      model_path: "/models/yolo_kfs.onnx"
      labels_path: "/models/labels_kfs.txt"
      conf_thresh: 0.50
      iou_thresh: 0.45
      input_w: 640
      input_h: 640

    mf_area:
      engine: aidlite
      model_path: "/models/qnn_yolo_mf.qnn236.ctx.bin"
      labels_path: "/models/labels_mf.txt"
      conf_thresh: 0.45
      iou_thresh: 0.45
      aidlite:
        framework_type: "QNN236"
        accelerate_type: "DSP"
        implement_type: "LOCAL"
        input_tensor: "images"
        output_tensors: ["_326", "_364", "_402"]
        output_layout: "yolov5_multi"
```

### 6.5 新增/替换 Profile 的最小流程（模板化）

1. 在 YAML 的 `vision.models` 新增一个 `model_id`（填好 `engine/model_path/labels/conf_thresh...`）。
2. 在 BT 需要切换处调用：
   - `<VisionSetModel model_id="你的model_id"/>` + `<VisionStart/>`，或
   - `<VisionStart model_id="你的model_id"/>`
3. 若希望默认启动即使用该模式：修改 `vision.default_model`。

## 7. 验收标准（建议用于后续实现验收）

- **BT 模板化切换**：在任意子树入口/任务阶段，通过 `VisionSetModel` 或 `VisionStart model_id=...` 触发切换后，可稳定切到对应 Profile，且不会崩溃、死锁或出现线程无法退出。
- **两种调用方式都可用**：
  - 方式一：先 `VisionSetModel` 再 `VisionStart`
  - 方式二：`VisionStart model_id="..."`
- **YAML 可配置**：仅通过 YAML 即可新增/替换模型 Profile，并为 Profile 选择 `onnxruntime` 或 `aidlite` 引擎。
- **失败可观测**：请求不存在的 `model_id` 或模型加载失败时，返回失败并使 `vision_ok` 可用于 BT 分支降级（例如直接跳过视觉）。
