# rc26_odom_interface 模块功能综述

## 1. 模块定位：我们为什么需要它？
`rc26_odom_interface` 是一个关键的“适配器”和“对齐工具”。
原本 `point_lio` 算出来的里程计是以“雷达启动时的位置”为原点的，而且它是相对于雷达坐标系（`lidar_frame`）的。但对于整个机器人系统（比如导航、底盘控制）来说，我们习惯以“底盘启动时的位置”为原点，并且关心的是底盘中心（`base_link`）在哪里。
这个模块的作用就是消除这种差异：它把 `point_lio` 输出的原始数据接过来，结合雷达和底盘的安装位置（外参），转换成全工程统一的 `odom -> base_link` 格式。这样，后续的模块就不需要操心“雷达装哪儿了”或者“原点在哪儿”，直接用标准的里程计数据就行。

## 2. 接口与交互：它是如何工作的？
它站在 SLAM 算法和上层应用之间，负责数据的标准化转发。

### 它需要什么（输入）
*   **原始位置（里程计）**：`point_lio` 发出来的 `state_estimation` 话题（`nav_msgs/Odometry`）。
*   **原始地图（配准点云）**：`point_lio` 发出来的 `cloud_registered` 话题（`sensor_msgs/PointCloud2`）。
*   **硬件关系（TF）**：它需要从 TF 树中查询底盘和雷达之间的固定安装位置（外参 `base_frame -> lidar_frame`）。

### 它产出什么（输出）
*   **标准里程计**：它发布标准的 `odom` 话题。这里的坐标系明确为 `odom_frame` 指向 `base_frame`，并且我们补全了速度信息（twist）。
*   **标准点云**：转发后的 `registered_scan`。注意，这个点云的坐标系和输出的里程计是一致的（都在 `odom_frame` 下），方便后续直接叠加显示或计算。
*   **坐标关系（TF）**：持续发布 `odom_frame -> base_frame` 的变换。这是整个 TF 树的躯干，保证了机器人位置的连续性。

### 关键配置（参数）
为了保证数据正确，这些参数不能填错：
*   **身份定义**：`odom_frame`, `base_frame`, `lidar_frame`。
*   **时间控制**：`tf_lookup_timeout_sec`（查 TF 等多久），`max_time_diff_sec`（点云和位置差多久算失效）。

## 3. 核心逻辑：怎么做对齐？
这部分是模块的灵魂，主要解决了两个问题：

1.  **空间对齐（坐标变换）**：
    *   Point-LIO 告诉我们的是：雷达相对于原点在哪里（`lidar_odom -> lidar`）。
    *   我们需要知道的是：底盘相对于原点在哪里（`odom -> base`）。
    *   **做法**：我们先查到雷达装在底盘的什么位置（`lidar -> base`），然后把这个关系叠加上去，算出一个修正后的变换。
    *   **容错**：我们会定期刷新这个外参关系。如果某次查 TF 失败了，只要之前成功过，我们会继续沿用旧的参数，保证车不会突然“瞎”了。但如果一开始就查不到，为了安全，我们会拒绝工作并报错。

2.  **时间对齐（数据守卫）**：
    *   **防止穿越**：点云和里程计应该是同一时刻的。如果现在的点云对应的是好几秒前的里程计（或者反过来），叠加起来就会有重影。我们设了个阈值 `max_time_diff_sec`，时间差太大的点云直接丢掉。
    *   **防止乱序**：如果因为网络波动，先发的数据后到了，我们会识别出来，只处理时间戳递增的数据，防止机器人“倒退”。

## 4. 速度补全：不仅仅是位置
Point-LIO 给出的主要是位置（Pose）。为了让底盘能闭环控制，我们还需要速度（Twist）。
我们通过“差分”来计算速度：看看这一帧和上一帧位置变了多少、角度转了多少，除以时间差，就得到了线速度和角速度。
*   **细节处理**：如果两帧时间间隔极短（`dt` 接近 0）或者异常长，为了防止算出来的速度无穷大（数值爆炸），我们会跳过这次计算。

## 5. 团队协作：与上下游的约定
1.  **对下（传感器处理）**：`rc26_sensor_scan` 模块非常信任我们。它默认收到的里程计是 `child_frame_id == base_frame` 的，且点云和里程计在同一个坐标系下。如果我们做不到，它那边的障碍物检测就会错位。
2.  **对上（启动管理）**：`rc26_bringup` 必须保证 TF 树里有 `base_link -> livox_frame` 的静态变换（通常在 URDF 或者 launch 文件里发）。如果这个关系不存在，我们根本不知道雷达装在哪儿，也就没法工作。
