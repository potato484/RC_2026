# RC26 决策模块 (rc26_decision) 设计综述

## 1. 模块定位与背景
`rc26_decision` 是整个系统的“大脑”，负责任务级的决策与流程编排。我们采用 **BehaviorTree.CPP** 作为核心框架，将复杂的比赛任务拆解为一个个可组合、可复用的行为节点。通过黑板（Blackboard）机制共享状态，我们实现了一个既能灵活调整任务顺序（可重排），又方便后续功能扩展（可扩展），同时运行状态一目了然（可观测）的任务逻辑系统。
此外，该模块还肩负着几个关键职责：与 MCU 进行底层动作指令的交互、协同 Nav2 完成导航任务，以及处理和判断台阶语义信息。

## 2. 行为树架构设计
为了保证逻辑的灵活性和可维护性，我们在架构上做了如下设计：
1.  **基于 XML 的流程配置**：
    我们使用 XML 文件来定义任务流程，并支持通过 `include` 标签引入子树。例如，主树 `main_tree.xml` 可以将 `mc_tree.xml`（移动底盘）、`mf_tree.xml`（多功能机构）、`combat_tree.xml`（对抗逻辑）等按需组合。这种“分而治之”的策略使得每个阶段的逻辑都可以独立维护，修改规则时不会牵一发而动全身。
2.  **自定义 BT 节点封装**：
    我们将导航控制、机械机构动作、条件判断等逻辑封装为具体的叶子节点。这意味着，当比赛策略调整时，我们往往只需要修改 XML 文件中的节点顺序或参数，而无需重新编译代码。
3.  **周期性 Tick 机制**：
    行为树以固定的周期（由 `tick_rate_ms` 参数控制）进行 Tick 更新。当整棵树返回 SUCCESS 或 FAILURE 时，Tick 会自动停止，防止对已完成的流程进行无意义的重复执行。

## 3. 黑板数据模型
为了降低各个 BT 节点之间的耦合度，我们强制要求通过黑板来共享数据。目前黑板上维护的核心数据主要包括：
1.  **串口通信状态**：
    包含共享的串口对象 `cmd_serial`，以及用于判断连接健康的 `cmd_serial_reconnecting` 和 `cmd_serial_reconnect_failed` 状态。
2.  **MCU 反馈信息**：
    既包含原始的反馈信号 `feedback_0xXX`，也包含解析后的语义布尔值（如 `grab_tip_done`、`assemble_done` 等）。这样，上层节点只需要关心“动作是否完成”，而不需要关心具体的通信协议细节。
3.  **环境与台阶语义**：
    如 `current_level`（当前层级）、`stair_delta`（台阶差）、`base_ground_stable`（地面是否平稳）等。这些数据是决策层判断能否执行上/下台阶动作或进行状态切换的关键依据。

## 4. 下位机交互机制（串口/心跳/反馈）
决策层与 MCU（下位机）的交互不仅是简单的指令发送，更是一套完整的闭环系统：
1.  **可配置的命令串口**：
    可以通过参数（`enable_cmd_serial`、`cmd_serial_port` 等）灵活开启或配置串口。如果串口打开失败，系统会发出明确的告警，方便上层做降级处理。
2.  **心跳保活机制**：
    系统通过定时器周期性发送心跳包（`sendHeartbeat()`），并由底层串口库自动处理失败计数与重连逻辑，确保链路的可靠性。
3.  **状态驱动的重连策略**：
    重连的开始、成功或失败都会实时更新到黑板中。行为树可以根据这些状态，动态选择是等待重连、终止任务还是切换到备用策略。
4.  **反馈驱动的流程控制**：
    MCU 的反馈不再是单纯的日志，而是直接驱动行为树流转的信号。回调函数会将协议数据映射为黑板上的布尔值，行为树节点据此精准判断动作是成功完成、失败还是发生了系统错误。

## 5. 台阶语义处理
决策模块会实时订阅 `rc26_base_ground` 的输出，并将以下关键信息写入黑板：
*   `base_ground/level` (Int32)：当前所处层级。
*   `base_ground/stair_delta` (Int8)：台阶高度差。
*   `base_ground/stable` (Bool)：地面平稳状态。
这些信息是“上/下台阶”动作的必要前置条件，同时也确保了只有在平稳路段才允许进入某些关键动作，保障了机器人的运行安全。

## 6. 导航系统集成 (Nav2)
我们通过标准的 Nav2 Action 接口与导航系统对接：
1.  **Action 驱动**：
    通过参数配置 Action 名称（默认 `navigate_to_pose`）和目标坐标系（默认 `map`），实现通用的导航控制。
2.  **全生命周期管控**：
    行为树节点不仅负责发送导航目标，还会持续轮询执行结果。一旦任务被 Halt 或中断，节点会立即取消导航 Action 并触发安全停车，确保机器人不会“失控”乱跑。

## 7. 配置与扩展性
为了适应多变的赛场环境，我们在配置上也留足了空间：
1.  **灵活的行为树文件加载**：
    可以通过 `tree_file` 参数指定启动时加载的 XML 文件。在 launch 启动脚本中覆盖此参数，即可快速切换不同的赛制或调试逻辑。
2.  **参数化的通信话题**：
    涉及 base_ground 的话题名称均支持参数化配置，方便在不同命名空间或集成方案下复用。
3.  **注意事项**：
    目前 `config/decision_params.yaml` 中可能存在一些冗余参数（如 CAN 里程计相关），这些是历史遗留或未来规划项，当前代码并未实际读取。在集成调试时，请以节点实际声明的参数为准，并逐步清理和对齐配置文件。
