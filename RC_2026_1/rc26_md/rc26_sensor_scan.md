# rc26_sensor_scan 模块说明

## 1. 模块定位与背景
`rc26_sensor_scan` 扮演着“数据清洗与对齐中心”的角色。在我们的系统中，直接来自底层的里程计位姿和激光雷达点云，往往存在时间戳微小偏差、坐标系定义不统一或某些信息（如速度 Twist）缺失的问题。
本模块的核心任务就是把这些原始数据进行严格的时间同步、坐标变换和信息补全，输出一套**标准、整齐、下游 Nav2 可直接消费**的数据包。简而言之，它是连接底层驱动（rc26_odom_interface）与上层导航算法（Nav2/定位/地形分析）的关键桥梁。

## 2. 核心功能：数据对齐与标准化
为了让导航系统“看”得更准、“动”得更稳，我们做了以下工作：

1.  **严格的时间同步**：
    *   我们使用 `message_filters` 同时订阅里程计（`odom`）和点云（`registered_scan`）。
    *   **守卫机制**：模块会检查两者的时间戳。如果时间差超过设定阈值（`max_time_diff_sec`），我们会认为这帧数据不可靠并直接丢弃。这能有效防止因为“点云与位置不匹配”导致的障碍物在地图上乱飘的问题。

2.  **坐标系一致性检查**：
    *   我们强制规定：里程计的 `child_frame_id` 必须是 `base_frame`，且点云必须与里程计处于同一个坐标系下。
    *   如果发现坐标系定义混乱（例如把不同机器人的数据混进来了），模块会拒绝处理或直接报错。这是一种防御性编程，确保整个 TF 树的纯净。

3.  **点云坐标转换**：
    *   上游输入的配准点云通常是在全局（odom）坐标系下的。为了方便下游模块（如 Costmap）基于传感器视角处理障碍物，我们会利用缓存的静态外参（`base_frame -> lidar_frame`），把输出点云转回到 **雷达坐标系（lidar_frame）** 下。

## 3. 重要特性：速度补全（Velocity Estimation）
Nav2 的控制器非常依赖里程计中的速度信息（`Twist`）来做预测和控制。如果上游只提供了“位置”，我们就需要自己计算“速度”。
*   **差分计算**：我们利用相邻两帧的位姿变化和时间差，估算出机器人的线速度和角速度。
*   **坐标转换**：按照 ROS 规范（REP-103），计算出的速度会被转换到 **机器人坐标系（base_frame）** 下，而不是保留在世界坐标系中。
*   **数值保护**：针对极短时间间隔（dt过小）或极小旋转角度的情况，我们做了特殊的数值保护处理，防止计算出的速度值飞升或发散。

## 4. 数据输出与 TF 发布
处理完成后，模块会向外发布以下标准数据：
1.  **标准的点云（scan_topic）**：坐标系为 `lidar_frame`，时间戳与里程计严格对齐。
2.  **完整的里程计（odometry_topic）**：包含位置、姿态以及我们计算出的速度信息。
3.  **TF 变换**：发布 `odom -> base_frame` 的 TF 变换。特别注意，这个 TF 的时间戳使用的是点云的时间戳，这样可以最大限度减少下游模块在查询坐标变换时的插值误差。

## 5. 模块依赖与集成
*   **上游依赖**：`rc26_odom_interface`。我们需要它提供初步的 `odom` 和 `registered_scan`，以及准确的静态外参 TF。
*   **下游用户**：
    *   **Nav2**：使用我们输出的带有速度信息的 `odometry` 进行路径规划和控制。
    *   **rc26_terrain**：利用对齐后的点云进行地形和台阶检测。
    *   **rc26_localization**：依赖稳定的 TF 树进行辅助定位。

总的来说，`rc26_sensor_scan` 虽然逻辑不复杂，但它像一个严谨的“安检员”，确保了流入导航系统的数据都是高质量、合规的。
