# 2026赛季 机器人导航点位获取与管理方案

## 1. 方案概述
本方案旨在解决 ROBOCON 2026 比赛中，机器人在 12m x 12m 场地内的高精度定位与导航挑战。

鉴于场地设施（如武馆、梅林、对抗区）的物理分布特性，以及高难度任务（机械臂抓取、兵器对接）对空间精度的严苛要求，仅依赖理论坐标无法消除实战中的累积误差。因此，本系统采用 **“理论推算全局导引 + 现场示教位姿修正 + 视觉末端伺服闭环”** 的三级导航策略，确保机器人既能快速到达作业区域，又能满足毫米级的作业精度。

### 1.1 工程对接与关键要素
为确保方案在现有工程架构中顺利落地，需重点关注以下技术协同点：

*   **定位基准统一**：弃用 AMCL，全面采用 `rc26_localization` 提供的 3D 点云匹配定位。所有点位数据必须基于底盘相对于地图的变换关系 (`map -> base_link`) 进行录制与回放。
*   **导航与作业解耦**：
    *   **Nav2 协议栈**：负责长距离、避障导航，将机器人引导至目标附近的“趋近点”（Approach Point）。
    *   **末端执行器**：负责从“趋近点”到“作业点”（Work Point）的精细操作，此阶段必须依赖视觉反馈进行闭环调整，严禁依赖开环坐标。
*   **红蓝方配置隔离**：针对红蓝场地镜像但梅林区高度分布不同的特性，建立独立的点位配置文件 (`waypoints_red.yaml` / `waypoints_blue.yaml`)，通过启动参数 (`team`) 动态加载。
*   **安全模式动态协同**：针对梅林区的高风险地形，集成 `rc26_nav_mode_manager`。点位数据需携带安全模式元数据，在进入/离开梅林区时自动切换跌落保护策略 (`MF_SAFE` / `MF_TRAVERSE` / `MF_EXIT`)。
*   **决策层接口迁移**：将 `rc26_decision` 中硬编码的 Waypoint 逻辑迁移为基于 YAML 的配置驱动模式，支持动态加载与热调整。
*   **地图一致性前置**：必须保证 Nav2 使用的 2D 栅格地图（`map_server`）与定位使用的 3D 点云先验（`prior_pcd_file`）在同一 `map` 坐标系下严格对齐，消除系统性偏差。

### 1.2 核心约束与前置条件
*   **硬性避障**：场地隔板与边界视为绝对障碍，路径规划必须严格遵守，触碰即视为任务失败（强制重试）。
*   **R1 通行限制**：R1 仅允许在通道内移动，除抓取 KFS 动作外，底盘不得接触梅林方块本体。
*   **R2 梅林拓扑约束**：R2 在梅林区仅允许在相邻方块（前后左右）间移动，严禁斜向跨越或落地。系统必须实现“邻接图构建 + 分步路点导航”以保证合规。
*   **TF 树完整性**：现场示教依赖 `map -> odom -> base_link` 变换链的实时稳定性。
*   **先验数据就绪**：必须提供与实地特征匹配的 2D 栅格地图与 3D 点云文件。

### 1.3 交付物清单
1.  **点位配置文件**：红/蓝两份 YAML（包含静态导航点、梅林锚点、导航语义参数）。
2.  **示教录制工具 (CLI)**：支持现场快速录制、更新、校验点位的 ROS 2 节点/脚本。
3.  **梅林拓扑算法**：基于锚点自动生成安全站位点及邻接路径规划逻辑。
4.  **标准化作业程序 (SOP)**：包含地图对齐校验、点位录制流程及赛前验收清单。

## 2. 坐标系定义与管理
### 2.1 坐标系标准
*   **场地坐标系 (Field Frame)**：理论参考系。原点定义为启动区特定角点，X 轴指向对抗区，Y 轴指向场地中心。仅用于策略推演。
*   **地图坐标系 (Map Frame)**：实际导航系。由 SLAM 建图原点决定。
    *   **策略原则**：所有导航点位均以 `map` 系为准。若建图原点发生漂移，优先通过重定位或地图整体校准解决，避免修改点位文件。

### 2.2 多队伍管理
采用文件隔离策略：`config/waypoints/waypoints_red.yaml` 与 `config/waypoints/waypoints_blue.yaml`。禁止在同一文件中通过逻辑分支处理红蓝差异，以降低现场误操作风险。

### 2.3 地图对齐校验 (SOP 核心步骤)
确保 2D 导航地图与 3D 定位点云在空间上的一致性是本方案生效的前提：
1.  **可视化检查**：在 RViz 中同时加载 2D Map、Point Cloud、Robot Model，观察静态吻合度。
2.  **物理闭环验证**：选取场地内 2~3 个几何特征明显的静态标志物（如围栏角点），控制机器人往返导航，测量 `map -> base_link` 的重复定位误差。
    *   **合格标准**：位置误差 ≤ 5cm，航向误差 ≤ 2°。若超标，必须重新校准地图或定位初值。

## 3. 关键区域导航策略

### 3.1 武馆区（取料与组装）
*   **启动点 (Start Pose)**：机器人上电复位位置。
*   **趋近点 (Approach Point)**：位于货架/长杆前约 1.0~1.5m 处，作为 Nav2 导航的终点。
*   **作业点 (Work Point)**：机械臂执行动作的最佳站位。需通过现场示教确定，并配合视觉伺服修正最终误差。
*   **组装点 (Assembly Point)**：双机器人协作区域，需考虑动态避让策略。

### 3.2 梅林区（R2 专属 - 拓扑生成）
梅林区由 12 个（4x3 矩阵）方块组成，采用参数化生成策略：
*   **安全站位点 (Safe Stand Pose)**：基于方块中心，叠加底盘半径与安全裕量 (`safe_offset`) 计算得出。
*   **生成逻辑**：
    利用示教的三个锚点（Block 1, 2, 4）构建局部坐标系，自动计算其余 9 个方块的中心坐标与站位点，确保点位与实际地形对其。
*   **模式切换**：
    *   方块内调整：`MF_SAFE` (防跌落开启)。
    *   跨越间隙：`MF_TRAVERSE` (防跌落暂时屏蔽，设超时保护)。
    *   离开梅林：`MF_EXIT`。

### 3.3 对抗区（射击与放置）
*   **关键路径**：坡道顶点、九宫格趋近线。
*   **末端操作**：射击位与放置位严重依赖实时视觉反馈，导航仅负责将其送入视觉捕获范围。

## 4. 详细实施方案

### 4.1 数据结构设计 (YAML)
文件结构需兼顾扩展性与易读性：

```yaml
header:
  version: "1.2"
  team: "red"
  frame_id: "map"

static_points:
  # 静态关键点：包含位姿与导航语义
  start_pose:
    x: 0.0
    y: 0.0
    theta: 0.0
    nav_mode: "Normal"         # 对应底盘/导航模式
    speed_mps: 1.5             # 巡航速度
    nav_safety_mode: "NORMAL"  # 安全策略
    tolerance: {xy: 0.05, yaw: 0.1}
    timeout_sec: 10.0

merlin_config:
  # 梅林区生成参数
  anchors: # 仅需示教3个锚点
    block_1: {x: 1.2, y: 3.4} # 基准点
    block_2: {x: 1.8, y: 3.4} # 横向参考
    block_4: {x: 1.2, y: 4.0} # 纵向参考
  params:
    safe_offset: 0.20   # 站位安全回退距离
    jump_margin: 0.20   # 跨越边缘预留
```

### 4.2 示教录制工具 (CLI)
开发专用 ROS 2 节点，通过命令行交互实现高效录制：
*   **核心功能**：
    *   监听 `/tf` 话题，实时获取 `map -> base_link` 变换。
    *   自动处理四元数到欧拉角的转换。
    *   支持 `record` (新增/更新)、`list` (查看)、`validate` (校验) 指令。
    *   **一键锚点录制**：`record_anchor <id>` 专门用于梅林区锚点采集。

### 4.3 梅林拓扑生成算法
1.  **输入**：Block 1, 2, 4 的示教坐标。
2.  **基底计算**：
    *   横向基向量 $V_x = \text{Norm}(P_2 - P_1)$，间距 $d_x = |P_2 - P_1|$
    *   纵向基向量 $V_y = \text{Norm}(P_4 - P_1)$，间距 $d_y = |P_4 - P_1|$
3.  **网格生成**：任意方块 $(r, c)$ 的中心坐标：
    $$ P_{r,c} = P_1 + (c-1) \cdot d_x \cdot V_x + (r-1) \cdot d_y \cdot V_y $$
4.  **安全修正**：最终站位 $P'_{r,c} = P_{r,c} - \text{safe\_offset} \cdot \text{Direction}(P_{r,c})$

### 4.4 数据驱动决策架构 (Data-Driven Decision Architecture)
为了实现“录制工具自动接入，行为树专注于决策逻辑”的目标，采用以下三层架构设计，确保导航数据与业务逻辑的完全解耦：

1.  **数据层 (Data Layer)**：
    *   由录制工具生成的 YAML 文件，存储 `名称 -> (坐标, 属性)` 的映射关系。
    *   **属性定义**：除基础位姿 $(x, y, \theta)$ 外，还包含容忍度 (`tolerance`)、超时时间、专属安全模式标记等元数据。

2.  **桥接层 (Bridge Layer - Blackboard Integration)**：
    *   **点位管理器 (Waypoint Manager)**：在 `rc26_decision` 启动时，解析 YAML 文件，并将所有点位数据自动注入到行为树的 **黑板 (Blackboard)** 中。
    *   **数据映射**：例如，YAML 中的点位 `rack_approach` 会被映射为黑板变量 `nav.points.rack_approach`，供行为树节点随时索引。

3.  **决策层 (Decision Layer - Behavior Tree)**：
    *   **通用导航节点 (`NavToSmartPoint`)**：
        *   **接口设计**：仅暴露一个输入端口 `target_name` (String)。
        *   **内部逻辑**：节点运行时，根据 `target_name` 从黑板查找实际坐标与属性，调用 Nav2 Action 执行移动。
        *   **执行结果**：`SUCCESS` (成功到达趋近范围)，`FAILURE` (路径受阻或超时)。
    *   **逻辑编排 (Sequence Logic)**：
        利用行为树的 **Sequence (顺序)** 节点串联“粗略导航”与“精细操作”，实现 **“导航管赶路，视觉管干活”** 的分层控制。
        *   **逻辑示例**：
            ```text
            [Sequence] 示例任务链
             ├── [Action] NavToSmartPoint (target_name="rack_approach")  <-- 1. 调取数据，粗略到达
             ├── [Condition] CheckVisualTarget (视觉检测)                <-- 2. 到达后判断环境
             └── [Fallback] 闭环精细操作
                  ├── [Sequence] 视觉伺服 & 抓取                         <-- 3. 视觉引导闭环
                  │    ├── [Action] VisualServoAlign (视觉对准)
                  │    └── [Action] GraspObject (执行抓取)
                  └── [Sequence] 异常恢复                                <-- 4. 容错处理
                       ├── [Action] RotateSearch (原地搜索)
                       └── [Action] RetryVisualServo (重试)
            ```

### 4.5 通用导航点接口与扩展机制 (Universal Waypoint Interface)
为统一管理全场导航任务，建立 **“导航即模式切换 (Navigation as Mode Switching)”** 的核心架构。该机制借鉴行为树中 **继承同步节点或异步节点** 的设计思想，将每一个导航点不仅仅定义为一个空间坐标，更定义为一种特定的 **“决策模式 (Decision Mode)”**。

#### 1. 模式切换与策略变换
在本系统中，“模式切换”的含义超越了简单的状态变更，它代表了机器人当前 **决策策略的根本变换**：
*   **策略继承与变换**：正如行为树中不同类型的节点继承了不同的执行特性，切换到一个特定的模式，就表明机器人当前的战术目标发生了改变。例如，在梅林区中切换模式，意味着“在梅林中拾取 KFS 的策略”发生了变换，此时系统必须立即执行这一新策略所定义的一系列行为。
*   **全场通用性**：这一逻辑并不局限于梅林区，同理适用于全场所有的非梅林点。无论是“组装点”还是“拾取点”，每一个导航点的激活都意味着机器人进入了一个新的模式，每一个点都需要执行其对应的决策行为（也就是切换模式）。

#### 2. 统一执行机制
基于上述思想，系统实现了对所有任务点的统一抽象：
*   **点位即决策**：系统不再区分“移动”与“作业”，而是将到达某个点位视为触发该点位对应模式的开关。
*   **自动行为加载**：一旦导航目标确定，系统即刻切换至目标点所绑定的模式。这确保了无论是在梅林复杂的动态环境中，还是在常规区域，机器人都能自适应地调用相应的感知、控制与执行算法，完成既定任务。

#### 3. 架构优势
*   **逻辑解耦**：将复杂的战术动作封装在独立的“模式”中，主导航逻辑只需关注模式的切换，无需处理具体执行细节。
*   **扩展便捷**：新增战术或调整现有策略时，只需修改或继承相应的模式定义，无需重构整体导航框架。

### 4.6 统一数据契约与执行接口 (Standardized Data Contract & Execution Interface)
为确保“导航即模式切换”设计思想的有效落地，并消除工程实践中的数据歧义，本系统制定了严格的数据与接口契约。这既是开发规范，也是模块间协作的硬性标准。

#### 1. 统一数据契约 (Unified Data Contract)
系统内流转的所有导航点位（无论是 YAML 静态加载，还是梅林算法动态生成），均必须封装为 **SmartWaypoint** 结构。严禁任何模块直接传递裸坐标数据 $(x, y, \theta)$，以确保语义的完整性。

*   **SmartWaypoint 数据结构定义**：
    *   **核心位姿 (`pose`)**：`geometry_msgs/Pose` (Map Frame)，定义目标点的空间位置。
    *   **容忍度 (`tolerance`)**：`NavTolerance`，定义该点位允许的 XY 位置误差与 Yaw 角度误差（例如：作业点需 $\pm 1cm$，而趋近点可放宽至 $\pm 10cm$）。
    *   **安全模式 (`nav_safety_mode`)**：`Enum/String`，指定导航至该点过程及到达后的底盘安全策略（如 `MF_SAFE` 开启防跌落保护，`MF_TRAVERSE` 允许跨越障碍）。
    *   **决策标签 (`strategy_tag`)**：`String`，即“模式 ID”。行为树根据此标签决定到达目标后激活的业务子树（如 `TAG_GRASP`、`TAG_SCAN`、`TAG_WAIT`）。
    *   **运动配置 (`speed_profile`)**：`String`，指定 Nav2 Controller 的动态参数（如 `SLOW` 对应精细对接模式，`FAST` 对应全场巡航模式）。

#### 2. 统一执行接口 (Unified Execution Interface)
行为树（Behavior Tree）与底层导航系统的交互，必须且只能通过单一通用节点 **`NavToSmartPoint`** 进行。严禁在行为树中绕过此接口直接调用 Nav2 Action。

*   **节点接口定义**：
    *   **Input**: `target_name` (String) —— 仅暴露语义化的点位名称，屏蔽底层数据解析细节。
*   **原子化执行序列**：
    1.  **索引 (Look-up)**：根据 `target_name` 从 Blackboard 或 YAML 配置中检索完整的 `SmartWaypoint` 数据包。
    2.  **模式切换 (Mode Switch)**：在下发移动指令前，自动调用 `nav_safety/set_mode` 服务，预先切换至目标点位要求的安全模式。
    3.  **执行 (Execute)**：调用 Nav2 `NavigateToPose` 接口，并将 `speed_profile` 透传给控制器以调整运动特性。
    4.  **反馈 (Feedback)**：实时监控导航状态。若遭遇“致命障碍”或“超时”，立即返回 `FAILURE`。
    5.  **后置条件 (Post-Condition)**：导航返回 `SUCCESS` 即表明机器人的物理状态与安全状态均已就绪，行为树随即根据 `strategy_tag` 切换至下一阶段的业务逻辑。

#### 3. 约束可验证化 (Verifiable Constraints)
为保障上述契约的严格执行，所有配置数据须经由工具链进行静态检查：
*   **拓扑合规性**：对于梅林区动态生成的点位，`validate` 工具必须校验其连通性，确保路径仅存在于相邻方块之间，**严禁生成对角线跨越路径**。
*   **红蓝同构性**：红蓝双方的 YAML 配置文件结构必须完全同构，仅允许坐标数值存在差异，严禁出现“红方包含某策略点而蓝方缺失”的逻辑不对称。

### 4.7 框架实现声明与用户自定义扩展 (Framework Implementation & Customization)
需要特别说明的是，本方案核心在于提供一个**标准化的导航与决策交互框架**，而非限定具体的所有业务模式。这与 `rc26_serial` 模块的设计哲学保持一致。

#### 1. 框架与实现的界限
*   **框架层 (Provided)**：本方案提供了 `SmartWaypoint` 数据结构、`NavToSmartPoint` 执行接口、YAML 配置文件解析器以及基础的模式切换机制（如 `nav_safety/set_mode`）。这些构成了系统的“骨架”，确保导航行为的可控性和数据流的规范性。
*   **用户实现层 (User Defined)**：具体的“模式”定义及其内部实现逻辑（例如：`TAG_GRASP` 具体应该调用哪些视觉节点、执行怎样的机械臂动作序列），属于用户的业务范畴。

#### 2. 极简接口参考 (Reference Design)
参考 `rc26_serial` 的设计，其通过 `SerialDriver` 类提供了极其简洁明了的通信接口（如 `sendCommand`, `sendPose`），而将复杂的底层协议解析和多线程管理封装在内部。

同理，本导航方案旨在为上层决策（Behavior Tree）提供类似的极简接口：
*   **用户侧调用**：仅需在行为树中配置 `NavToSmartPoint(target_name="xxx")`。
*   **框架侧封装**：自动处理坐标变换、安全模式校验、底层 Nav2 Action 客户端管理、异常状态监控等复杂流程。

用户应专注于定义新的 `strategy_tag` 并在行为树中实现对应的业务子树，而无需关心机器人“如何安全地到达”目标点，从而实现类似于调用 `sendCommand` 一样简单直观的导航体验。

## 5. 现场操作流程 (SOP)

### 阶段一：环境准备
1.  **系统启动**：底盘、传感器、定位 (`rc26_localization`)、导航 (`Nav2`) 上线。
2.  **对齐校验**：执行 2.3 节所述的地图对齐检查。
3.  **服务检查**：确认 `nav_safety/set_mode` 服务在线。

### 阶段二：示教录制
1.  运行录制工具：`ros2 run rc26_decision point_recorder --ros-args -p team:=red`
2.  **静态点录制**：
    *   遥控机器人至目标位姿。
    *   输入 `record <name>`（如 `rack_approach`）。
3.  **梅林锚点采集**：
    *   将机器人底盘中心对准 Block 1 中心。
    *   输入 `record_anchor block_1`。
    *   依次完成 Block 2 和 Block 4。
4.  **数据固化**：输入 `save` 保存并退出，检查生成的 YAML 文件。

### 阶段三：验证验收
1.  **完整性校验**：运行 `validate` 命令检查 YAML 格式及数值合理性。
2.  **空跑测试**：重启决策节点，观察日志确认点位加载成功。依次触发各关键点导航，观察路径规划是否合理、安全模式切换是否及时。

## 6. 验收标准
| 检查项 | 达标标准 | 备注 |
| :--- | :--- | :--- |
| **坐标系一致性** | 2D Map 与 3D PCD 物理特征重合度 > 95% | 基础前提 |
| **定位精度** | 静态往返定位误差 < 5cm | 保证导航可重复性 |
| **梅林合规性** | 仅生成相邻移动路径，无对角跨越，无异常跌落 | 规则红线 |
| **故障处理** | 导航受阻/超时能自动触发回退或重试逻辑 | 鲁棒性要求 |
| **数据安全** | 红蓝方配置互不干扰，支持快速回滚 | 赛场容错 |
